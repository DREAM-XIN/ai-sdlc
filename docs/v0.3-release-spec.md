# AI-SDLC v0.3 release specification

Status: Review Draft — author-side hardening applied

Tracking issue: #205

This document defines the implementable release boundary for AI-SDLC `0.3.0`. The broader product direction is described in `docs/v0.3-product-vision.md`.

## 1. Release objective

v0.3.0 must prove that an AI client can operate an already-installed AI-SDLC Feature through a durable, typed, recoverable orchestration layer without moving lifecycle authority into the model, worker, client session, or Operator store.

The required vertical slice is:

```text
Installed project
→ AI client capability discovery / status / inbox
→ start or discover active durable Operation
→ Developer
→ Independent Reviewer
→ Remediation when required
→ Independent Re-review
→ QA
→ NEEDS_USER / DONE
```

Normal progression through this slice MUST NOT require repeated user `continue` messages.

Full Requirement/Design automation and Project Takeover are not release blockers for `0.3.0`; they are v0.3.x follow-up work after the vertical loop is stable.

## 2. Non-negotiable authority model

### 2.1 Operator authority

The Operator MAY:

- inspect durable project and Feature state;
- invoke the canonical typed API;
- request Commander/Router planning;
- atomically claim one bounded semantic dispatch;
- dispatch an allowed role worker;
- collect a structured Worker Result;
- invoke a trusted role-specific Result Translator;
- request Event validation/Persist through existing trusted lifecycle paths;
- wait for external work and resume from durable callbacks;
- perform deterministic recovery;
- create Decision and Notification records;
- present a user-friendly projection.

The Operator MUST NOT:

- directly modify an authoritative Feature Manifest;
- construct arbitrary lifecycle state changes outside trusted translators;
- PASS or waive a Gate;
- override revision checks;
- treat chat or Operator projection state as Feature authority;
- merge protected branches without exact authorization;
- expand trusted authorization policy;
- collapse Developer, Reviewer and QA authority into one execution identity.

### 2.2 No second Feature truth

Operator persistence MAY contain operation identity, append-only orchestration events, dispatch claims, waiting references, retries, callbacks, Decisions and Notifications.

Operator persistence MUST NOT become authoritative for:

- current Feature stage;
- lifecycle artifact status;
- Gate status;
- Feature revision;
- release authority.

Lifecycle decisions MUST re-read authoritative AI-SDLC state.

## 3. Canonical typed API

The canonical Operator API MUST be transport-independent. MCP and other clients are adapters over this contract.

### 3.1 Frozen v1 identifier

The initial canonical API identifier is:

```text
ai-sdlc.operator/v1
```

Every canonical request and response MUST identify this API version.

`system.capabilities` MUST return the supported API versions and capabilities. A request using an unsupported version MUST fail with `UNSUPPORTED_API_VERSION` and return the supported versions without executing a semantic write.

Backward-incompatible changes require a new canonical API version.

### 3.2 Minimum v0.3.0 capabilities

The canonical v1 surface required for the release slice is:

```text
system.capabilities
project.inspect
feature.status
operator.inbox
operation.start
operation.status
operation.resume
operation.cancel
decision.list
decision.respond
notification.list
notification.ack
```

`operator.inbox` is the new-session discovery primitive. Scoped to an authorized user/repository context, it MUST be able to discover:

- unfinished Operations;
- Operations in `NEEDS_USER` or `BLOCKED`;
- pending Decisions;
- unread Notifications.

A new AI session MUST NOT need a previous chat transcript or pre-known `operation_id` to discover actionable Operator state.

`operation.resume` is for explicit recovery from `BLOCKED` or another policy-permitted suspended state. Routine `WAITING_EXTERNAL` callbacks MUST resume automatically without a user or client calling `operation.resume`.

### 3.3 Identity model

Authenticated calls MUST distinguish at least:

- the human/user principal when a user is represented;
- the AI client/adapter identity;
- the trusted service/runtime identity performing the call;
- the requested capability.

A client identity MUST NOT be treated as equivalent to human authorization merely because the client acts on the user's behalf.

### 3.4 Semantic write contract

Every semantic write MUST carry or derive:

- target repository identity;
- Feature id where applicable;
- operation id where applicable;
- expected Feature revision where lifecycle-sensitive;
- idempotency key;
- authenticated identities;
- requested capability;
- trusted policy context.

Lifecycle-sensitive calls MUST fail closed on stale revision and return structured information for safe reread/replan.

### 3.5 Error model

Canonical errors MUST distinguish at least:

```text
INVALID_REQUEST
UNSUPPORTED_API_VERSION
CAPABILITY_UNAVAILABLE
UNAUTHORIZED
POLICY_DENIED
STALE_REVISION
ALREADY_CLAIMED
ALREADY_APPLIED
EXTERNAL_WAIT
NEEDS_USER
BLOCKED
TRANSIENT_FAILURE
INTERNAL_FAILURE
```

Clients MUST NOT parse human text to determine retry or user-action semantics.

## 4. Client adapters and conformance

v0.3.0 MUST provide an MCP adapter over the canonical v1 API.

A read-only MCP slice MAY land first for early dogfood, but the release MUST include at least one supported AI client adapter that can perform the required release-slice writes, including `operation.start`, `operation.cancel` and `decision.respond` when those capabilities are policy-allowed.

At least two materially independent client integration paths MUST pass the canonical conformance suite before release. The common conformance subset MUST include:

```text
system.capabilities
feature.status
operator.inbox
operation.start
operation.status
decision.list
decision.respond
notification.list
```

The second path MUST NOT merely rename or wrap the same adapter implementation without independently exercising the canonical boundary.

Adapters MUST NOT expose arbitrary Manifest/Event/shell mutation as substitutes for canonical lifecycle operations.

## 5. Worker Result boundary and trusted translation

v0.3.0 MUST reuse existing task/execution/result concepts and add only a common trusted envelope where useful.

### 5.1 Trusted wrapper vs untrusted worker payload

The collector/runtime MUST construct trusted context from the dispatch and trusted execution receipt. The Worker MUST NOT self-assert these trusted fields.

Conceptually:

```text
Trusted Result Envelope
├── trusted_context
│   ├── operation_id
│   ├── dispatch_id
│   ├── target_repository
│   ├── feature_id
│   ├── expected_revision
│   ├── target_ref
│   ├── task_id
│   ├── role
│   └── runtime_receipt_identity
└── worker_payload
    ├── status
    ├── artifacts
    ├── evidence
    ├── findings
    └── role_specific_payload
```

Worker-supplied `identity`, `role`, `task`, dispatch identity, or execution metadata MUST NOT override trusted context.

### 5.2 Prohibited Worker output

A Worker Result MUST NOT contain an arbitrary executable Feature Event, arbitrary state patch, Gate mutation or revision mutation.

Fields equivalent to unrestricted `proposed_events` are forbidden.

### 5.3 Trusted translators

Lifecycle mutations derived from Worker Results MUST be produced by deterministic trusted role-specific translators:

```text
Developer Result → Developer Result Translator
Reviewer Result  → Review Verdict Translator
QA Result        → Verification Verdict Translator
```

A translator MUST:

- consume trusted dispatch/receipt context rather than Worker-asserted identity;
- validate the role-specific result schema;
- bind to expected Feature/revision/ref;
- reject stale or mismatched results;
- emit only Event shapes allowed for the role/task;
- preserve existing Event validation and Persist authority.

A Worker-controlled prompt, template or model output MUST NOT define the translator's Event mutation rules.

## 6. Normative v0.3.0 Operation Journal

v0.3.0 uses a repository-backed trusted Operation Store in the trusted control repository. It MUST NOT live on the target Feature branch.

### 6.1 Protected state ref

The reference implementation MUST persist Operator state on a dedicated protected control-plane state ref resolved from trusted installation/control configuration, conceptually:

```text
refs/heads/ai-sdlc-operator-state
```

The exact ref name MAY be configurable by trusted installation policy, but a target Feature branch MUST NOT select or modify it.

Feature workers and target Feature branches MUST NOT receive credentials that can write this state ref.

### 6.2 Versioned append-only layout

The v1 reference layout is conceptually:

```text
state/operator/v1/
├── operations/<operation-id>/events/<sequence>-<event-id>.json
├── claims/dispatch/<dispatch-key>.json
├── claims/feature/<target-repo-hash>/<feature-id>.json
├── decisions/<decision-id>.json
├── notifications/<notification-id>.json
└── projections/<operation-id>.json
```

Operation Event schema version:

```text
ai-sdlc.operation-event/v1
```

Operation Events and consumed claim records MUST be immutable through the trusted write path. A cached projection MAY be replaced for performance, but MUST be rebuildable from immutable events and trusted records.

### 6.3 Writer authority

Only trusted Operator/Collector/Recovery components MAY append Operation Events or mutate bounded claim/projection/Decision/Notification state according to their schemas.

Role Workers MUST NOT write the Operation Store directly.

### 6.4 Atomic journal/claim writes

The reference repository-backed implementation MUST use Git ref compare-and-set semantics for state-ref updates:

1. read the current trusted state-ref SHA;
2. construct the bounded journal/claim update against that exact tree;
3. update the protected state ref only if the expected ref SHA is still current;
4. on conflict, re-read and re-evaluate before retrying.

A semantic dispatch claim MUST be committed successfully before a Worker is launched.

If the claim already exists after a conflict/re-read, the caller MUST return the existing dispatch or `ALREADY_CLAIMED`; it MUST NOT launch another Worker.

### 6.5 Operation events

Representative events include:

```text
operation.started
operation.resumed
operation.cancel.requested
operation.cancelled
operation.superseded
dispatch.claimed
worker.dispatched
worker.completed
worker.result.orphaned
callback.received
persist.requested
persist.confirmed
operation.waiting
decision.requested
decision.responded
notification.enqueued
operation.blocked
operation.completed
operation.recovered
```

### 6.6 Retention and rebuild

Records required for active Features, outstanding Decisions, unresolved retries, dispatch correlation, security audit or release evidence MUST NOT be deleted by normal retention.

Loss of a cached projection MUST be recoverable from the journal.

Loss/corruption of the Operation Store MUST NOT corrupt Feature authority. Recovery MUST re-read authoritative Feature state and durable PR/CI/Worker/Event receipts; if an active dispatch cannot be proven absent or safely correlated, recovery MUST stop `BLOCKED` rather than launch speculative work.

## 7. Active Operation and semantic dispatch uniqueness

### 7.1 One active Operation per Feature

For a given target repository and Feature, at most one nonterminal active Operation generation may own automatic progression at a time.

`operation.start` MUST atomically claim the Feature's active-operation slot. If an active Operation already exists, an equivalent start request MUST return that Operation rather than create a second progression owner.

A recovery takeover MAY supersede an older Operation only through a trusted atomic handover that records `operation.superseded` and proves the prior generation can no longer dispatch.

### 7.2 Semantic dispatch identity

Before Worker launch, the trusted Operator MUST atomically claim a semantic dispatch identity that binds at least:

```text
target_repository
feature_id
expected_revision
current_stage
task_identity
role
operation_generation
```

Equivalent retries resolve to the same claim or `ALREADY_CLAIMED`.

Invariant:

> For one target repository, Feature, revision, stage, semantic task and operation generation, at most one active valid Worker dispatch may exist.

Concurrency tests MUST exercise two Runners racing before Worker launch.

## 8. Execution and cancellation model

v0.3.0 MUST use short durable executions plus event-driven resume. It MUST NOT depend on one long-lived chat process or indefinitely running workflow loop.

Typical flow:

```text
Operator execution
→ re-read authoritative state
→ Plan
→ atomic active-operation / dispatch claim
→ dispatch Worker
→ record WAITING_EXTERNAL
→ execution ends

Worker / CI callback
→ trusted collector
→ correlate operation + dispatch
→ translate / Persist when allowed
→ trigger resume
→ re-read authoritative state
→ Plan again
```

Closing the AI client session MUST NOT cancel an active Operation.

### 8.1 `operation.cancel`

`operation.cancel` stops automatic progression for the current Operation; it is not Feature cancellation.

Cancellation MUST be recorded atomically in the trusted Operation Store.

If lifecycle Persist was already durably confirmed before cancellation, that Feature change remains authoritative.

After cancellation is durably recorded:

- no new Worker may be dispatched by that Operation;
- no not-yet-started translation/Persist may advance lifecycle state from that Operation;
- an already-running Worker may still finish because remote execution may not be revocable;
- its receipt/result MAY be recorded for audit but MUST be marked orphaned and MUST NOT automatically advance lifecycle state;
- a later Operation may adopt useful orphaned work only after re-read/replan and an explicit trusted adoption rule.

### 8.2 `feature.cancel`

`feature.cancel` is a separate lifecycle operation and MUST use the existing trusted lifecycle/Event authority. Cancelling an Operation MUST NOT imply Feature cancellation.

## 9. Operator state projection

Top-level user-visible states:

```text
RUNNING
WAITING_EXTERNAL
NEEDS_USER
BLOCKED
DONE
CANCELLED
```

`WAITING_EXTERNAL` is non-user wait only:

```text
WAITING_WORKER
WAITING_CI
WAITING_PR
WAITING_CALLBACK
```

`NEEDS_USER` includes:

```text
NEEDS_CLARIFICATION
NEEDS_AUTHORIZATION
NEEDS_ACCEPTANCE
NEEDS_CREDENTIAL_SETUP
```

`DONE` and `CANCELLED` are terminal Operation states.

`BLOCKED` is a stable suspended state, not terminal Feature authority. It MAY be resumed only when durable facts and policy establish a safe recovery path.

## 10. Authorization policy

Authorization policy MUST NOT be controlled by the current Feature branch.

Trusted authorization sources are:

- protected default-branch configuration;
- installation-level configuration;
- trusted control-repository policy.

Ordinary engineering context MAY come from Project Adapter data subject to trusted baseline constraints.

A Feature branch MAY tighten permissions but MUST NOT expand them.

Authorization policy changes MUST follow an independently reviewed trusted path; a Feature governed by the policy change MUST NOT approve that change for itself.

Authorization checks SHOULD bind a trusted policy source ref/digest for audit and MUST re-evaluate current trusted policy when the authorized operation is consumed. A stale Decision MUST never broaden permissions after policy changes.

## 11. Decision model

Broad consent operations such as `feature.approve` are forbidden.

Authorization-bearing Decisions MUST bind, as applicable:

```text
decision_id
decision_type
feature_id
operation_id
expected_revision
target_ref
candidate_head_sha
allowed_choices
trusted_policy_ref_or_digest
requested_by
requested_at
expires_at
status
responded_by_user
responded_via_client
responded_at
selected_choice
```

A generic user statement such as `yes` only satisfies a Decision after the client resolves the concrete pending Decision and submits an allowed choice through `decision.respond`.

Expired, already-consumed, stale-revision, wrong-ref, wrong-SHA or policy-invalid Decisions MUST NOT authorize an operation.

Concurrent responses to the same Decision MUST resolve through idempotency/CAS so at most one valid response is consumed.

Decision persistence MUST store only minimum auditable facts. Full chat transcripts, secrets and unnecessary sensitive free-form content MUST NOT be persisted as Decision evidence.

## 12. Notification Outbox

v0.3.0 MUST provide a durable Notification Outbox.

Minimum types:

```text
decision.requested
operation.blocked
operation.completed
authorization.expiring
```

Notification states MAY include:

```text
PENDING
DELIVERED
READ
EXPIRED
```

`notification.ack` is a bounded user/client operation that MAY advance delivery/read acknowledgement for an authorized notification. It MUST NOT alter Feature lifecycle state or authorization outcomes.

Push-capable adapters MAY deliver proactively. Clients without push MUST discover unread Notifications through `operator.inbox` / `notification.list` in a new session.

Notification delivery failure MUST NOT alter lifecycle authority or silently convert `NEEDS_USER` into progress.

## 13. Recovery contract

Recovery MUST be deterministic and policy-driven rather than free-form model judgment.

| Condition | Required behavior |
|---|---|
| stale Feature revision | re-read + replan |
| duplicate semantic request | return existing Operation/dispatch or idempotent success |
| duplicate Event | no duplicate lifecycle transition |
| duplicate callback | no duplicate side effect |
| callback out of order | correlate and ignore/block safely |
| Worker timeout | bounded retry or BLOCKED by policy |
| Worker failure | classify; retry/remediate/block by policy |
| CI failure | remediation path when lifecycle permits |
| Reviewer requests changes | durable Developer remediation + independent re-review |
| PR head changes | invalidate stale result/evidence bound to old head |
| Persist response lost | query durable Event/receipt before retry |
| Event applied but acknowledgement lost | detect already-applied outcome |
| permission/credential missing | NEEDS_USER / NEEDS_CREDENTIAL_SETUP |
| AI client closes | no impact on durable Operation |
| two Operators resume concurrently | active-operation claim + dispatch claim + state-ref CAS prevent duplicate launch |
| Operation cancelled while Worker runs | record result as orphaned; no automatic lifecycle mutation after cancel |
| trusted Operation Store unavailable | recover from durable facts or fail BLOCKED without speculative dispatch |

## 14. Acceptance boundary

Under the default standard Feature policy, AI/Product agents MAY produce an Acceptance Recommendation but MUST NOT synthesize Human/Product Acceptance Evidence solely from an AI PASS recommendation.

Default concept:

```text
AI/Product Acceptance Recommendation
→ NEEDS_USER / NEEDS_ACCEPTANCE
→ Human/Product Decision
→ Acceptance / release evidence
```

Policy-automated acceptance for bounded low-risk profiles is outside the default v0.3.0 release proof.

## 15. Required implementation workstreams

### A. Canonical API + client adapters

Deliver:

- `ai-sdlc.operator/v1` schemas;
- capability discovery;
- `operator.inbox` discovery;
- structured errors;
- actor/client/service identity contract;
- expected-revision and idempotency contracts;
- read-only MCP bootstrap followed by required release-slice writes;
- a second independent client integration path;
- tool schema and multi-client conformance tests.

### B. Durable Operation Store

Deliver:

- `ai-sdlc.operation-event/v1` schema;
- protected trusted control-plane state ref;
- append-only immutable events;
- deterministic projection;
- Git ref CAS writer;
- active-operation claim;
- semantic dispatch claim;
- callback correlation;
- cancellation/orphan-result handling;
- Operation recovery primitives.

### C. Operator vertical loop

Deliver:

```text
Implementation-ready Feature
→ Developer
→ independent Reviewer
→ remediation
→ independent Re-review
→ QA
→ NEEDS_USER / DONE
```

This workstream MUST reuse existing Commander/Router/Event/Persist and existing reviewer/QA autonomy rather than fork lifecycle logic.

### D. Recovery and concurrency

Deliver section 13 recovery behavior, including replay, cancellation race and concurrent-resume tests.

### E. Decision, authorization and notification

Deliver:

- bounded Decision schema;
- exact authorization binding;
- policy ref/digest audit binding;
- `decision.respond`;
- `operation.cancel` vs `feature.cancel` separation;
- Notification Outbox and `notification.ack`;
- new-session `operator.inbox` discovery.

### F. Planning/release draft validation

Before implementation progress relies on `release/v0.3.0-draft.yaml`, provide a deterministic schema/validator for the planning manifest and wire it into repository CI. Green v0.2 release-readiness validation alone is not evidence that the v0.3 planning manifest is valid.

## 16. Explicitly deferred from v0.3.0

Not required for `0.3.0`:

- full Product/Requirement/Architecture/Design lifecycle automation;
- automatic Project Takeover from an uninstalled repository;
- project upgrade automation;
- custom Web Dashboard;
- organization portfolio orchestration;
- complex multi-repository central scheduling;
- dynamic provider cost optimization;
- automatic production deployment;
- unaudited high-risk Gate automation.

## 17. Required tests

### 17.1 Tool contract

Must cover:

- exact v1 API identifier and unsupported-version response;
- capability discovery;
- `operator.inbox` discovery without previous operation id;
- valid/invalid schemas;
- stable structured errors;
- semantic idempotency;
- expected-revision rejection;
- unsupported capability handling.

### 17.2 Authorization adversarial

Must cover:

- Feature branch policy expansion rejected;
- broader credential scope rejected;
- Developer Gate PASS rejected;
- Reviewer prohibited source mutation rejected;
- stale authorization replay rejected;
- wrong-ref authorization replay rejected;
- wrong-SHA merge authorization rejected when applicable;
- expired Decision rejected;
- concurrent Decision responses consume at most one valid choice.

### 17.3 Operation/replay/concurrency

Must cover:

- duplicate callback;
- out-of-order callback;
- duplicate Worker completion;
- two Runners race for active Operation;
- two Runners race for same dispatch before Worker launch;
- Persist succeeds but response is lost;
- projection deletion/rebuild;
- AI client session loss/resume;
- `operation.cancel` racing a Worker callback;
- orphaned Worker result does not auto-Persist after cancel;
- Operation Store recovery fails closed when outstanding dispatch cannot be proven absent.

### 17.4 Multi-client conformance

At least two materially independent client integration paths MUST pass the same canonical release-slice conformance subset.

At least one supported AI client adapter MUST exercise release-slice writes end-to-end.

### 17.5 Planning manifest validation

CI MUST validate `release/v0.3.0-draft.yaml` against a deterministic planning contract while it is the active v0.3 planning manifest.

## 18. Required dogfood matrix

### Scenario A — happy path

An already-installed project reaches QA/stable completion without repeated user `continue` messages.

### Scenario B — review remediation

Independent Reviewer requests changes; Operator dispatches Developer remediation, independent re-review and QA without user lifecycle driving.

### Scenario C — session recovery

AI client session terminates while active. Durable execution reaches an external wait or stable stop. A new session discovers relevant Operation/Decision/Notification state through the canonical discovery surface.

### Scenario D — failure injection

At least stale revision, duplicate callback, concurrent active-operation/dispatch claims, cancellation race and Persist acknowledgement loss are exercised without duplicate lifecycle or Worker side effects.

### Scenario E — external transport

The release-selected dogfood matrix MUST include external target execution and preserve v0.2 public/private trusted transport boundaries. The final exact public/private matrix is a release decision recorded in `release/v0.3.0-draft.yaml` before candidate cut.

## 19. Release blockers

`0.3.0` MUST NOT be cut while any are unresolved:

1. Worker Result can carry arbitrary executable Feature Event/state mutation.
2. Worker-controlled identity/role/task metadata can override trusted dispatch/receipt context.
3. A Worker can bypass its deterministic role-specific trusted Translator.
4. User authorization is not bound to exact Feature/revision/ref/SHA/policy context when applicable.
5. Feature branch can expand its authorization policy.
6. More than one nonterminal active Operation can automatically own the same target Feature without trusted supersession.
7. One semantic task at one Feature state can create more than one active valid Worker dispatch.
8. Operation Store is not on a trusted protected control-plane boundary.
9. Repository-backed dispatch/active-operation claim is not atomic under concurrent Runners.
10. Operation Journal is not append-only/immutable or projection cannot be rebuilt deterministically.
11. Loss/corruption of Operator projection/store can cause speculative duplicate work rather than safe recovery/BLOCKED.
12. Duplicate callback/request can produce duplicate side effects.
13. `operation.cancel` and `feature.cancel` are ambiguous or a cancelled Operation can auto-Persist a late Worker result.
14. Human approval is classified as non-user `WAITING_EXTERNAL`.
15. New sessions cannot discover unfinished Operations, pending Decisions and unread Notifications without prior chat identifiers.
16. Offline users prevent durable progress to a stable stop condition.
17. Normal release-slice execution requires routine manual GitHub operations after installation authorization.
18. Typed API lacks exact versioning/capability discovery.
19. No supported client adapter can execute required release-slice writes.
20. Canonical API fails conformance on two independent client integration paths.
21. Notification read/ack state has no bounded canonical mutation path.
22. Decision persistence stores unnecessary full chat/sensitive content by default.
23. Human Acceptance Evidence can be synthesized solely from an AI recommendation under default policy.
24. `release/v0.3.0-draft.yaml` has no deterministic CI validation contract before implementation depends on it.
25. Current v0.2 lifecycle authority, Event validation, revision CAS or independent Gate guarantees are weakened.

## 20. Release completion definition

v0.3.0 is complete when a user can use a supported AI client to discover and operate the required Feature slice through `ai-sdlc.operator/v1`, leave the session, return from a new session, and observe a correct durable result without learning or manually manipulating internal AI-SDLC protocol state.

The release narrative is:

> Users express intent. AI operates the workflow. AI-SDLC enforces policy. Independent workers perform bounded work. GitHub preserves the durable facts.
