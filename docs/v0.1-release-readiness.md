# v0.1 release readiness

AI-SDLC `0.1.0` is the first externally consumable protocol/reference-implementation baseline. The repository may freeze and validate the baseline before publishing a GitHub Release or version tag.

## Baseline definition

The machine-readable release contract is:

```text
VERSION
release/v0.1.0.yaml
```

`release/v0.1.0.yaml` declares:

- every normative JSON Schema;
- every supported Workflow Profile;
- reference control-plane entry points;
- required operating/security documentation;
- CI validators that must remain wired into the repository validation workflow;
- reference runtime support level;
- known blockers that must clear before tag publication.

`python scripts/validate_release_readiness.py` verifies the declaration against the repository.

## What v0.1 means

The `0.1.0` baseline includes a working control plane for:

```text
Bootstrap
→ Feature Manifest
→ Commander / Orchestrator
→ Runtime Router
→ ChatGPT Web manual Task Package
→ Feature Event / Evidence
→ Event Inbox
→ Transition
→ Persistence Plan
→ revision-safe Git persistence
→ next Commander state
```

It also includes Project Adapter and cross-repository GitHub installation contracts.

It does **not** claim that every planned runtime is executable. `gh-aw` and Agent Orchestrator remain integration/routing targets until their adapters satisfy the security and Evidence contracts.

## Compatibility

The baseline uses the policy in `docs/protocol-versioning.md`.

Important pre-release compatibility decisions already preserved in v0.1 include:

- legacy Feature Manifests without `revision` are interpreted as revision 0;
- low-level Feature Events may omit `id`/`expected_revision` for earlier 0.1 compatibility;
- repository Event Inbox persistence is intentionally stricter and requires explicit identity/revision preconditions;
- Project Adapter is optional; projects without it retain the reference Commander's prior default behavior.

No migration from an earlier public AI-SDLC release is required because `0.1.0` is the first externalized baseline.

## Release gates

A GitHub Release/tag must not be published until:

1. full repository CI is green on `main`;
2. `validate_release_readiness.py` passes;
3. no release-blocking Security Review finding is open;
4. every blocker declared in `release/v0.1.0.yaml` is cleared;
5. the second-repository cross-repository installation dogfood has passed using an immutable AI-SDLC SHA;
6. `CHANGELOG.md` accurately describes known limitations.

The current external blocker is Issue #52: the StarringV6Test install is prepared but GitHub private Actions Access must be enabled on the `ai-sdlc` repository before the real second-repository Action can be downloaded.

## Production pin policy

A human-facing release tag may identify the release, but target-repository workflows should pin the reviewed full commit SHA. Caller templates intentionally use `REPLACE_WITH_AI_SDLC_FULL_SHA` until installation substitutes that SHA.

## Milestone #1 completion

Milestone #1 originally required:

- JSON Schema validation;
- protocol compatibility/versioning rules;
- examples for core protocol objects;
- schema/semantic CI;
- dogfooding feedback to be incorporated.

Those requirements are now covered by the repository baseline, including semantic validators, Feature Manifest/Event contracts, runtime routing, security hardening and dogfood findings. After this release-readiness feature passes, Milestone #1 can be closed.

## Legacy dogfood Issue cleanup

The first dogfood cycle intentionally over-modeled Requirements/Design/Plan/Gate/Artifact evidence as separate GitHub Issues. That experiment showed unacceptable bookkeeping overhead.

The accepted model is now:

```text
Feature Issue
  + Feature Manifest
  + repository Artifacts/Evidence
  + true executable Work Unit Issues when needed
```

Obsolete bookkeeping-only Issues should be closed with a supersession explanation; repository artifacts and Git history retain their audit trail.
