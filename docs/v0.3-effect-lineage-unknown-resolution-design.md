# v0.3 Effect Lineage and UNKNOWN Resolution Design

Status: **Author proposal — independent protocol review required**

Tracking issue: #219  
Release planning parent: #205  
Related completed Features: `F-OPERATOR-OPERATION-STORE-0001` (#214), `F-OPERATOR-VERTICAL-LOOP-0001` (#216)

This document is an architecture/design proposal only. It does not modify the frozen v0.3 Release Spec on `main`, does not change runtime code, does not retroactively reopen #214/#216, and does not constitute an independent review or release-readiness claim.

## 1. Why this design is required

The current v0.3 Operator implementation intentionally separates Operation generation from external semantic-effect identity. The exact `semantic_effect_key` excludes Operation generation and binds:

```text
target_repository
feature_id
expected_revision
current_stage
task_identity
role
candidate_head_sha_or_null
```

The stable `external_dispatch_key` is then bound to that exact reservation. This correctly prevents generation takeover from minting a new external identity for the same exact reservation.

However, Feature revision, stage and candidate facts are part of the exact key. A later authoritative Feature revision or candidate projection can therefore produce a different exact `semantic_effect_key` even when the intended real-world work is still the same unresolved external effect.

The current vertical runtime also advances its expected Feature revision after trusted Persist, so revision changes are normal lifecycle facts rather than proof that a prior external effect is semantically unrelated.

The missing protocol concept is a durable, revision-independent continuity domain above exact reservations.

This design introduces **Effect Lineage** and makes unresolved predecessor state authoritative across Feature revision, candidate projection, Operation generation and, where necessary, Operation replacement.

## 2. Safety goals

The design MUST preserve these release semantics:

- no speculative duplicate external dispatch;
- one stable external identity for one exact external dispatch attempt;
- deterministic recovery after crash/restart/takeover;
- trusted correlation of existing external work;
- one authorized Feature Persist for one exact bounded lifecycle write;
- no claim of external exactly-once execution.

The design additionally MUST ensure:

1. Feature revision change alone never proves that an unresolved predecessor is a new external effect.
2. Candidate SHA change alone never releases UNKNOWN blocking.
3. Generation takeover never releases lineage blocking.
4. Concurrent planners cannot create two launch-eligible descendants from one unresolved predecessor.
5. Human/trusted recovery cannot become an unrestricted `retry`, `ignore`, `force`, or “new lineage” escape hatch.

## 3. Non-goals

This work does not:

- implement the full Decision/Notification product;
- add a generic human override API;
- change Feature lifecycle authority;
- weaken Reviewer/QA candidate-head binding;
- redesign the Worker Runtime transport contract;
- perform #221 real-runtime fault injection;
- promise exactly-once behavior from an external system.

## 4. Terminology

### 4.1 Exact semantic effect

An **exact semantic effect** is the currently implemented revision/stage/task/role/candidate-bound launch identity represented by one `semantic_effect_key`.

It remains intentionally precise and immutable.

### 4.2 Effect lineage

An **effect lineage** is the durable continuity domain for one logical real-world work slot across exact-state changes that do not, by themselves, prove the old external effect is unrelated.

A lineage may contain zero or more exact effect members over time, but at most one member may be launch-eligible while a predecessor remains unresolved.

### 4.3 Predecessor

A **predecessor** is the prior exact effect member whose external-state resolution constrains whether a proposed successor may become launch-eligible.

### 4.4 Successor proposal

A **successor proposal** is a trusted planner result saying current authoritative Feature truth now wants an exact effect different from the current lineage member.

A proposal is not an external reservation and does not receive a new `external_dispatch_key` until lineage safety permits activation.

### 4.5 Conclusive external-state proof

A conclusive proof is trusted evidence that resolves the predecessor sufficiently for the next lineage transition. Approved proof classes are defined in Section 10.

## 5. Effect Lineage identity

### 5.1 `effect_lineage_id`

Introduce a stable identifier:

```text
effect_lineage_id
```

Conceptually:

```text
effect_lineage_id = sha256(canonical_json(effect_lineage_material))
```

### 5.2 Lineage material

The lineage material MUST be derived by trusted planner/runtime code from durable Feature/task facts and role-specific semantics. It MUST include enough information to identify one logical work slot, for example:

```text
target_repository
feature_id
operation_profile
effect_kind
role
causal_work_id
external_effect_scope
```

The material MUST NOT include, merely as identity-changing fields:

```text
operation_id
operation_generation
expected_revision
current_stage snapshot revision
candidate_head_sha
chat/session identity
runner identity
```

Those values remain exact-fence facts on the exact semantic member; they do not automatically create a new lineage.

### 5.3 `causal_work_id`

`causal_work_id` is the durable root that explains why the logical work exists. It MUST come from trusted durable lifecycle facts, not from a Worker or client-supplied random value.

Examples for the current vertical loop:

- implementation work: the durable lifecycle episode that moved `implementation` into its active execution episode;
- first code review: the durable code-review stage-start episode;
- remediation: the authoritative remediation task id;
- re-review: the authoritative remediation task id that causally requires the re-review;
- verification: the durable verification-stage start episode.

A future implementation MAY derive a compact deterministic token from the exact Feature Event/task record that created the episode. The important property is that unrelated revision increments or candidate projection changes do not silently replace that causal root.

### 5.4 `external_effect_scope`

`external_effect_scope` is a role-specific normalized descriptor of the external work domain. It prevents one overly broad lineage from serializing genuinely independent effects.

It must be produced by trusted code. Examples might distinguish two independent external work units within one lifecycle task if the profile later supports them.

### 5.5 Proving semantic distinctness

A proposed effect is allowed to use a different lineage only when trusted durable facts establish a different `causal_work_id`, `effect_kind`, role, or `external_effect_scope` according to reviewed profile semantics.

The following facts alone are insufficient to prove distinctness:

- revision `R -> R+1`;
- candidate SHA change;
- Operation generation change;
- Operation id change;
- process restart;
- user text saying “retry”, “ignore”, or “start over”.

## 6. Durable lineage model

### 6.1 Additive store layout

Keep the existing `state/operator/v1` root and immutable exact reservation model. Add a separate immutable lineage namespace:

```text
state/operator/v1/
├── reservations/external/<semantic-effect-key>.json
├── lineages/<effect-lineage-id>/anchor.json
├── lineages/<effect-lineage-id>/members/<semantic-effect-key>.json
├── lineages/<effect-lineage-id>/proposals/<proposal-id>.json
├── lineages/<effect-lineage-id>/events/<sequence>-<event-id>.json
└── lineage-projections/<effect-lineage-id>.json    # rebuildable cache only
```

The existing reservation file remains immutable and does not need to be rewritten.

### 6.2 Lineage anchor

`anchor.json` is create-once immutable and binds the canonical lineage material plus trusted provenance:

```text
effect_lineage_id
lineage_schema_version
canonical_lineage_material
created_at
created_by_trusted_component
trusted_context_digest
```

Any attempt to reuse the same lineage id with different canonical material fails closed.

### 6.3 Exact lineage member

A member record is immutable and binds:

```text
effect_lineage_id
semantic_effect_key
predecessor_semantic_effect_key | null
relation: ROOT | SUCCESSOR
exact_semantic_material_digest
created_operation_id
created_generation
created_at
trusted_context_digest
```

Member status is not mutated in place. Activation, resolution, adoption and retirement are derived from append-only lineage events.

### 6.4 Successor proposal

When current authoritative truth wants a different exact semantic key but the predecessor is unresolved, the planner creates an immutable successor proposal instead of a new external reservation.

A proposal binds at least:

```text
proposal_id
effect_lineage_id
predecessor_semantic_effect_key
proposed_exact_semantic_material
proposed_semantic_effect_key
proposed_operation_id
proposed_generation
proposed_feature_revision
proposed_stage
proposed_candidate_head_sha
reason/provenance digest
```

A proposal has **no independent external dispatch identity**.

### 6.5 Lineage event journal

Introduce a separate schema, conceptually:

```text
ai-sdlc.effect-lineage-event/v1
```

Minimum event types:

```text
lineage.member.activated
lineage.successor.proposed
lineage.blocked-on-predecessor
lineage.external-state.correlated
lineage.resolution.recorded
lineage.receipt.adopted
lineage.member.retired
lineage.successor.activated
```

The exact final event vocabulary is an implementation detail for a later reviewed Feature, but the semantic transitions in this document are normative.

### 6.6 CAS and concurrency

Lineage planning MUST use the same protected-state-ref compare-and-set discipline as the Operation Store.

Before activating any successor, trusted code reconstructs the lineage from immutable history and proves that:

- the expected predecessor is still the current lineage leaf;
- no incompatible active/proposed descendant already won;
- predecessor blocking state is resolved according to Section 10;
- current Feature/candidate fences still match the proposed successor;
- the current Operation generation is authorized to continue orchestration.

If two planners race, only one CAS commit may establish the next active descendant. The loser re-reads and converges to the winning lineage state.

## 7. Predecessor and blocking semantics

### 7.1 Structural relation

For exact members in the same lineage:

```text
effect K0
   ↓ predecessor_of
effect K1
   ↓ predecessor_of
effect K2
```

The relation is an ordered chain for launch-eligible members in v0.3.0. Branching active descendants are forbidden.

### 7.2 `blocks_on`

`blocks_on` is a derived safety relation, not a client-controlled flag.

A successor proposal is blocked when its predecessor is in any state where the control plane cannot prove that activating a new independent external effect is safe.

Blocking states include at least:

```text
LAUNCH_AUTHORIZED_UNCONFIRMED
UNKNOWN
LAUNCHED_AWAITING_CORRELATION
LEGACY_UNRESOLVED_LINEAGE
```

### 7.3 `supersedes`

`supersedes` means current authoritative Feature truth no longer wants the predecessor's exact work product as the current desired exact effect.

It is an **intent relation only**.

`supersedes` MUST NOT itself release predecessor blocking and MUST NOT authorize a new external launch.

### 7.4 `adopts`

`adopts` means trusted recovery has correlated an already-launched predecessor external effect/receipt and is using that existing external effect as the authoritative launch occurrence for this lineage position.

Adoption never launches a new external effect.

Whether a returned Worker result may advance current Feature truth remains separately subject to exact revision/ref/candidate and trusted translator/Persist rules.

## 8. Reservation and launch planning protocol

The lineage gate moves **before** creation of a new independent exact reservation.

### 8.1 First member

If no lineage exists:

1. derive lineage material and exact semantic material;
2. atomically create lineage anchor;
3. create the root member;
4. create the existing exact semantic reservation and stable `external_dispatch_key`;
5. proceed through the existing dispatch claim and `dispatch.launch.authorized` fence.

### 8.2 Exact replay

If the current lineage member already has the same `semantic_effect_key`, reuse the existing reservation and stable `external_dispatch_key` under existing idempotency/fencing rules.

### 8.3 Different exact key with unresolved predecessor

If current truth proposes exact key `K1` while predecessor `K0` is unresolved:

1. record/reuse a successor proposal for `K1`;
2. record derived blocking against `K0`;
3. do **not** create a new exact external reservation for `K1`;
4. do **not** mint a new `external_dispatch_key` for `K1`;
5. project Operation/lineage state as `BLOCKED` with a machine-readable reason.

This is the core rule that closes the revision/candidate escape hatch.

### 8.4 Predecessor conclusively NOT_LAUNCHED

If trusted resolution proves `K0` was not launched:

- an exact retry of `K0` uses the same existing `external_dispatch_key` and normal launch authorization fences;
- if current truth now wants different exact work `K1`, the system may retire `K0` as not-launched and atomically activate `K1`, creating a new reservation/key only after the retirement proof is durable.

### 8.5 Predecessor conclusively LAUNCHED

If trusted resolution proves `K0` was launched:

- correlate/adopt the existing receipt;
- never launch `K0` again;
- do not activate a successor merely because its candidate/revision differs;
- first process/correlate the existing result through exact current applicability rules.

If the old launched result is later conclusively inapplicable/obsolete, it may be recorded as an orphaned/obsolete outcome. A genuinely required successor may then be activated only after the prior launched effect is durably known and the planner proves the successor is new required work rather than a duplicate of the still-unknown predecessor.

## 9. External launch state model

The current runtime lookup contract remains:

```text
lookup(external_dispatch_key)
  -> NOT_LAUNCHED
  -> LAUNCHED(receipt)
  -> UNKNOWN
```

Lineage safety additionally distinguishes the interval after launch authorization but before a conclusive trusted lookup/receipt:

```text
LAUNCH_AUTHORIZED_UNCONFIRMED
```

This state is derived from durable `dispatch.launch.authorized` without a later conclusive observation. It blocks successors exactly like `UNKNOWN` because missing local acknowledgement does not prove launch absence.

A lineage predecessor is considered resolved for successor activation only by one of the trusted resolution classes below.

## 10. UNKNOWN resolution protocol

A generic retry is not a resolution.

A resolution record MUST name an allowed outcome and carry evidence sufficient for that outcome.

### 10.1 `CORRELATE_EXISTING_RECEIPT`

Use when trusted runtime/gateway evidence proves the predecessor external key was launched and identifies the existing receipt/execution.

Required evidence includes:

```text
predecessor semantic_effect_key
predecessor external_dispatch_key
trusted runtime/gateway identity
receipt identity
receipt binding/digest sufficient to prove correlation
observation time/provenance
```

Result:

- predecessor becomes conclusively launched/correlated;
- no relaunch is allowed;
- existing callback/result recovery continues through normal trusted collector/translator rules;
- any successor remains non-launchable until current applicability is deterministically resolved.

### 10.2 `PROVE_NOT_LAUNCHED`

Use when a trusted runtime/gateway or other approved authoritative source proves that the predecessor external key did not launch.

Result:

- exact predecessor retry may use the same external key after all current fences pass; or
- if the old exact work is obsolete and a proposed successor is current, the predecessor may be retired as not-launched and the successor may be activated in one lineage-CAS transition.

### 10.3 `RETIRE_OBSOLETE_NO_DUPLICATE_PROVEN`

Use only when trusted evidence proves that activating the successor cannot duplicate the predecessor's real-world effect even though the prior local state was unresolved.

Acceptable proof must establish one of the following kinds of safety under reviewed runtime-specific policy:

- authoritative external invalidation/cancellation proving the predecessor can no longer execute;
- authoritative external namespace/scope separation proving the successor cannot duplicate the predecessor effect;
- another trusted proof at least as strong as `NOT_LAUNCHED` for duplicate-effect purposes.

The following are explicitly **not** sufficient:

- candidate SHA changed;
- Feature revision changed;
- task was replanned;
- Operation was cancelled;
- generation changed;
- user says “ignore it”;
- local callback/event is missing.

### 10.4 `BLOCKED`

If no trustworthy proof exists, the only valid outcome is to remain `BLOCKED`.

This is a safe terminal-for-now orchestration condition, not Feature authority and not a failure to be bypassed with a new key.

## 11. Human / trusted recovery authority

### 11.1 Bounded authority

Introduce a trusted internal concept:

```text
EffectResolutionAuthority
```

This is not a generic user override and does not require implementing the complete Decision/Notification product in #219.

The authority source MUST come from protected/default-branch, installation-level, or trusted-control policy. Feature branches, Workers, callbacks and ordinary AI clients cannot grant themselves this authority.

### 11.2 Who may resolve

Policy may authorize:

- a trusted recovery service acting on conclusive runtime evidence;
- a specifically authorized human principal acting through a bounded recovery workflow;
- a future bounded Decision flow whose allowed choices are predeclared by trusted policy.

A Worker whose own dispatch is being resolved MUST NOT self-authorize a safety-bypassing resolution.

### 11.3 Exact binding

Every resolution MUST bind at least:

```text
resolution_id
target_repository
feature_id
effect_lineage_id
predecessor_semantic_effect_key
predecessor_external_dispatch_key
current_operation_id
current_operation_generation
current_feature_revision
current_target_ref
current_candidate_head_sha_when_applicable
successor_proposal_id_when_applicable
successor_proposed_semantic_effect_key_when_applicable
allowed_resolution_choice
trusted_policy_ref_or_digest
resolver_identity
evidence_refs_and_digests
resolved_at
```

The resolution command must re-read the current lineage/Feature state under CAS. If the predecessor, lineage leaf, candidate, successor proposal, policy or Operation owner has changed, the decision is stale and rejected.

### 11.4 Allowed choices

The bounded choice set for v0.3 effect safety is:

```text
CORRELATE_EXISTING_RECEIPT
PROVE_NOT_LAUNCHED
RETIRE_OBSOLETE_NO_DUPLICATE_PROVEN
REMAIN_BLOCKED
```

There is no `FORCE_RETRY`, `IGNORE_UNKNOWN`, `DROP_RESERVATION`, `NEW_KEY_ANYWAY`, or equivalent choice.

### 11.5 Resolution does not dispatch

A resolution record only changes lineage eligibility/state.

After resolution, the trusted planner must re-read current Feature truth and pass normal reservation, claim, launch authorization, role/candidate, cancellation and generation fences before any external call.

Human authority therefore cannot directly cause an unfenced launch.

### 11.6 Audit

Resolution evidence and policy provenance are durable append-only lineage facts. Audit must answer:

- who resolved;
- under which trusted policy;
- which exact lineage/effect/key was resolved;
- what external evidence was relied on;
- what successor, if any, became eligible;
- why the action could not duplicate the predecessor effect.

## 12. Runtime contract compatibility

The Worker Runtime / trusted gateway contract does not need a new transport primitive for lineage:

```text
dispatch(external_dispatch_key, payload)
lookup(external_dispatch_key)
  -> NOT_LAUNCHED
  -> LAUNCHED(receipt)
  -> UNKNOWN
```

Effect Lineage is enforced in the trusted control plane before reservation activation/dispatch.

The runtime need not understand `effect_lineage_id` to provide stable-key launch/lookup semantics, although trusted observability may include it as correlation metadata.

The rules remain:

- exact replay of one reservation keeps the same stable external key;
- generation takeover keeps the same exact reservation/key;
- an unresolved predecessor prevents a new independent successor key;
- a successor may receive a new external key only after predecessor safety is conclusively resolved and the successor is activated;
- a conclusively launched predecessor is correlated/adopted rather than relaunched.

This design deliberately does **not** claim external exactly-once execution.

## 13. Restart and generation takeover

Given:

```text
G:
lineage L
exact effect K
external key E
UNKNOWN
```

and then runner crash:

1. lineage `L`, member `K`, reservation and `E` remain immutable durable state;
2. trusted takeover may move Operation ownership from `G` to `G+1`;
3. `G+1` reconstructs the same lineage state before planning external work;
4. `G+1` may query/correlate `E`;
5. `G+1` cannot activate a new independent descendant while `K` is unresolved;
6. revision or candidate changes observed after takeover can create only a blocked successor proposal until `K` is resolved.

Generation is orchestration ownership, never lineage identity and never UNKNOWN resolution evidence.

## 14. Stale / obsolete candidate handling

### 14.1 Candidate changed but logical effect is equivalent

Example:

```text
review candidate A -> UNKNOWN
candidate changes to B for an unrelated projection/update
same logical review episode remains active
```

The trusted planner derives the same lineage from the durable causal review episode. Candidate B changes the exact semantic key but not the lineage.

Result:

- create/reuse a successor proposal for B;
- block on predecessor A;
- no new external reservation/key for B while A is unresolved.

### 14.2 Old work truly obsolete

If current Feature truth makes predecessor exact work obsolete:

- record `supersedes`/obsolete intent;
- do not discard the unresolved predecessor;
- require `PROVE_NOT_LAUNCHED`, `CORRELATE_EXISTING_RECEIPT`, or `RETIRE_OBSOLETE_NO_DUPLICATE_PROVEN` before successor activation.

If predecessor is confirmed LAUNCHED, correlate it. The result may be orphaned/rejected for current Feature Persist if stale, but knowledge that it launched is still necessary before a new successor can safely proceed.

### 14.3 Genuinely different new effect

A new lineage is allowed only when reviewed profile semantics plus durable causal facts prove a genuinely different work slot/effect scope.

Changing candidate/revision alone does not create that proof.

## 15. Compatibility and migration

### 15.1 Release Spec impact

This design changes normative release effect-safety semantics. Therefore the frozen v0.3 Release Spec must not be silently edited on `main`.

A separate Release Spec amendment proposal must receive an independent exact-head review/freeze decision before implementation or release reliance.

### 15.2 Operation Store schema impact

The preferred migration is additive:

- keep `state/operator/v1`;
- keep existing immutable exact reservation files unchanged;
- keep existing `semantic_effect_key` semantics unchanged;
- add `ai-sdlc.effect-lineage/v1` anchor/member/proposal/event schemas;
- add deterministic lineage projection/rebuild logic;
- add lineage gating before creation/authorization of a new exact reservation.

This minimizes regression risk to completed #214/#216 behavior.

### 15.3 Operation Event version

A canonical `ai-sdlc.operation-event/v2` bump is not required merely to add lineage because lineage authority can live in a separate append-only lineage journal.

Existing Operation Events may optionally carry lineage references for audit after implementation, but the cross-Operation/cross-revision authoritative relation belongs in the lineage store.

If implementation later requires backward-incompatible changes to the Operation Event envelope itself, that must be separately reviewed and versioned.

### 15.4 Canonical API version

No `ai-sdlc.operator/v1` bump is required by this design because no existing public request/response meaning needs to become backward-incompatible.

The bounded resolution authority may remain trusted-internal until the later Decision/Authorization workstream exposes a reviewed user-facing path.

If a future public capability exposes new mandatory fields or changes existing capability semantics incompatibly, normal canonical API versioning rules apply.

### 15.5 Legacy reservations without lineage

Legacy reservations MUST remain readable.

For old reservations that lack lineage metadata/membership:

- trusted migration may attach a new immutable lineage anchor/member around the unchanged reservation when the durable causal work identity can be reconstructed safely;
- conclusive terminal/concluded old effects may be imported as resolved members;
- unresolved, UNKNOWN, or launch-authorized-unconfirmed legacy reservations MUST fail closed until lineage is established;
- if trusted code cannot safely determine the overlapping lineage scope, the Feature/task scope is quarantined as `LEGACY_UNRESOLVED_LINEAGE` and new potentially overlapping launches are blocked.

Migration MUST NOT infer “different effect” solely from old revision/candidate mismatch.

### 15.6 Deployment compatibility

Before lineage enforcement is enabled in production, old trusted Operator writers that do not understand lineage gating must be quiesced/fenced. Mixed old/new writers against the same protected state ref are unsafe because the old writer could ignore lineage artifacts.

The implementation Feature must define a bounded rollout/migration sequence that prevents old writers from authorizing new external launches after lineage enforcement becomes authoritative.

### 15.7 Impact on #214

#214 remains valid for:

- immutable Operation/reservation/claim facts;
- stable external key per exact reservation;
- launch linearization;
- UNKNOWN fail-closed behavior;
- generation takeover fencing;
- cancellation and Persist linearization.

The new protocol adds a higher-level cross-exact-effect gate. It does not rewrite #214 history.

### 15.8 Impact on #216

#216 remains valid for:

- Developer -> Reviewer -> Remediation -> Re-review -> QA orchestration;
- trusted collector provenance;
- exact candidate/result binding;
- role independence;
- bounded restart/takeover.

The later implementation must change dispatch planning so the vertical executor derives/consults lineage before it creates a new exact semantic reservation. Worker Result/translator authority does not move.

## 16. Deterministic adversarial test design

The implementation Feature must add deterministic tests at minimum for the following cases.

### 16.1 UNKNOWN at R -> unrelated revision R+1 -> same work

Expected:

- same lineage id;
- new exact semantic material may produce proposed key K1;
- K1 remains a proposal only;
- no new external reservation/key/launch while predecessor K0 is UNKNOWN.

### 16.2 UNKNOWN at R -> candidate changed but effect equivalent

Expected:

- same lineage id from same causal work root;
- candidate-changed exact effect is blocked on predecessor;
- candidate SHA alone cannot retire predecessor.

### 16.3 Predecessor proves NOT_LAUNCHED

Expected:

- conclusive durable resolution;
- exact retry reuses same key, or obsolete predecessor is retired and successor activation becomes eligible;
- any new successor reservation is created only after resolution is durable.

### 16.4 Predecessor proves LAUNCHED

Expected:

- existing receipt correlated/adopted;
- no relaunch/new key for equivalent effect;
- result remains subject to current exact applicability/Persist fences.

### 16.5 No trustworthy proof

Expected:

- lineage and Operation remain `BLOCKED`;
- generic resume/retry/ignore cannot change launch eligibility.

### 16.6 Generation takeover preserves blocking lineage

Expected:

- G -> G+1 changes ownership only;
- same lineage/predecessor/external key remains authoritative;
- no descendant activation while predecessor unresolved.

### 16.7 Concurrent planners

Use an explicit CAS barrier:

- two planners propose descendants of the same predecessor;
- at most one proposal/activation becomes current according to deterministic conflict rules;
- no two active launch-eligible descendants and no two independent external keys.

### 16.8 Stale manual/trusted resolution

Resolution must be rejected when any bound fact changed, including:

- wrong lineage id;
- wrong predecessor semantic key;
- wrong external key;
- wrong Operation/generation;
- stale Feature revision/ref;
- stale candidate head;
- wrong successor proposal;
- expired/changed trusted policy;
- mismatched evidence digest.

### 16.9 Cancelled predecessor remains unresolved

Expected:

- Operation cancellation does not retire UNKNOWN lineage state;
- a later Operation for the same causal work cannot launch a successor until approved resolution.

### 16.10 Legacy unresolved reservation

Expected:

- missing lineage metadata does not permit a new revision/candidate launch;
- safe migration creates lineage around the existing reservation when possible;
- otherwise fail closed with `LEGACY_UNRESOLVED_LINEAGE`.

## 17. Required invariants for implementation review

A later implementation may choose different class/file names, but independent review must prove all of these semantic invariants:

1. `semantic_effect_key` remains an exact immutable-state identity.
2. `effect_lineage_id` is stable across revision/candidate/generation changes that do not alter the causal work slot.
3. New independent external reservation creation is lineage-gated.
4. UNKNOWN or launch-authorized-unconfirmed predecessor blocks successor reservation/launch.
5. Candidate/revision/generation changes cannot release the block.
6. Conclusive LAUNCHED resolution adopts/correlates; it never relaunches.
7. Conclusive NOT_LAUNCHED resolution permits only normal fenced retry or safely activated successor.
8. Obsolete retirement requires durable no-duplicate proof.
9. Concurrent planners cannot activate sibling descendants.
10. Resolution authority is bounded, exact-state-bound, policy-bound and auditable.
11. Legacy no-lineage unresolved state fails closed.
12. External exactly-once is not claimed.

## 18. Recommended lifecycle after this design

Because #219 changes the normative frozen release contract, the legal sequence is:

```text
#219 author design + Release Spec amendment proposal
        ↓
independent Release Spec Amendment / Protocol Reviewer
        ↓
REWORK or PASS FOR AMENDMENT FREEZE
        ↓
if PASS: apply/freeze exact normative amendment through protected-main PR
        ↓
create a new formal implementation Feature under normal AI-SDLC lifecycle
        ↓
Requirement / independent Requirement Review
        ↓
Design / independent Design Review
        ↓
Plan / Implementation / independent Code Review / QA / Acceptance
        ↓
#221 real-runtime fault injection only after approved implementation exists
```

This preserves the frozen baseline, role independence and the completed status of #214/#216 while making the new protocol gap explicit and reviewable.
