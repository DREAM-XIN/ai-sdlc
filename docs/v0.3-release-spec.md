# AI-SDLC v0.3 release specification

Status: Review Draft — re-review required

Tracking issue: #205

Review baseline superseded: `de2cc6c8aa40adb6c550babc4443f792f4a0fe71`

This document defines the implementable release boundary for AI-SDLC `0.3.0`. The broader product direction remains in `docs/v0.3-product-vision.md`.

## 1. Release objective

v0.3.0 proves that supported AI clients can operate an already-installed AI-SDLC Feature through a durable, typed, recoverable Operator without moving lifecycle authority into the model, worker, client session, or Operator store.

Required vertical slice:

```text
Installed project
→ AI client capability/status/inbox
→ start or discover durable Operation
→ Developer
→ Independent Reviewer
→ Remediation when required
→ Independent Re-review
→ QA
→ NEEDS_USER / DONE
```

Normal progression through this slice MUST NOT require repeated user `continue` messages.

Full Requirement/Design automation and Project Takeover are deferred to v0.3.x and MUST NOT block v0.3.0.

## 2. Authority invariants

The Operator MAY inspect state, plan, claim bounded work, dispatch role workers, collect results, invoke trusted translators, request existing Feature Event/Persist paths, recover deterministic failures, and create bounded Decision/Notification records.

The Operator MUST NOT:

- directly edit authoritative Feature Manifests;
- construct arbitrary lifecycle mutations outside trusted translators;
- PASS or waive Gates on its own authority;
- override optimistic revision checks;
- treat chat or Operator projection state as Feature authority;
- broaden authorization policy;
- merge protected branches without exact authorization;
- collapse Developer, Reviewer and QA into one execution identity.

Feature lifecycle truth remains derived from authoritative AI-SDLC state. Operation state is orchestration metadata only.

## 3. Canonical Typed API

### 3.1 Version

The canonical API identifier for v0.3.0 is:

```text
ai-sdlc.operator/v1
```

Every request and response MUST identify the API version. `system.capabilities` MUST return supported API versions and capabilities. Unsupported versions MUST fail as `UNSUPPORTED_API_VERSION` without executing semantic writes.

### 3.2 Required capabilities

```text
system.capabilities
project.inspect
feature.status
operator.inbox
operation.start
operation.status
operation.resume
operation.cancel
decision.list
decision.respond
notification.list
notification.ack
```

`operator.inbox` is the new-session discovery primitive. An authorized client MUST be able to discover unfinished Operations, `NEEDS_USER`/`BLOCKED` Operations, pending Decisions, and unread Notifications without knowing an `operation_id` from a prior chat.

Routine `WAITING_EXTERNAL` callbacks resume automatically. `operation.resume` is reserved for explicit policy-permitted recovery from a suspended state such as `BLOCKED`.

### 3.3 Identity and semantic writes

Authenticated calls MUST distinguish human principal, AI client adapter identity, trusted service/runtime identity, and requested capability. AI client identity MUST NOT itself imply human authorization.

Every semantic write MUST carry or derive:

- target repository;
- Feature id where applicable;
- Operation id/generation where applicable;
- expected Feature revision where lifecycle-sensitive;
- idempotency key;
- authenticated identities;
- requested capability;
- trusted authorization-policy context.

### 3.4 Error model

Clients MUST receive structured errors rather than parse human text. Minimum errors:

```text
INVALID_REQUEST
UNSUPPORTED_API_VERSION
CAPABILITY_UNAVAILABLE
UNAUTHORIZED
POLICY_DENIED
STALE_REVISION
ALREADY_CLAIMED
ALREADY_APPLIED
SUPERSEDED_GENERATION
CANCELLED_OPERATION
EXTERNAL_WAIT
NEEDS_USER
BLOCKED
TRANSIENT_FAILURE
INTERNAL_FAILURE
```

## 4. AI Client adapters and conformance

v0.3.0 MUST ship at least two materially independent, supported **AI client adapters** over the canonical API. MCP MAY be one adapter.

Both AI client adapters MUST pass the same canonical conformance subset:

```text
system.capabilities
feature.status
operator.inbox
operation.status
decision.list
notification.list
```

Both adapters MUST additionally prove canonical request/response versioning, structured errors, identity propagation, and unsupported-capability behavior.

At least one of the two supported AI client adapters MUST execute the release-slice writes end-to-end, including as applicable:

```text
operation.start
operation.cancel
decision.respond
notification.ack
```

The second adapter MAY remain read-oriented for the end-to-end dogfood, but it MUST still be a genuine supported AI client adapter and MUST exercise the canonical boundary independently. Renaming or thinly wrapping the same adapter implementation does not count as independent conformance.

Adapters MUST NOT expose arbitrary Manifest/Event/shell mutation as substitutes for canonical operations.

## 5. Worker Result boundary and immutable candidate binding

### 5.1 Trusted context vs Worker payload

Trusted context MUST be constructed by trusted runtime/collector code from dispatch records and execution receipts. Workers MUST NOT self-assert translator-driving identity.

Conceptual envelope:

```text
Trusted Result Envelope
├── trusted_context
│   ├── operation_id
│   ├── operation_generation
│   ├── dispatch_id
│   ├── target_repository
│   ├── feature_id
│   ├── expected_revision
│   ├── target_ref
│   ├── candidate_pr_number          # when candidate-bound
│   ├── candidate_head_sha           # required for Reviewer/QA
│   ├── task_id
│   ├── role
│   └── runtime_receipt_identity
└── worker_payload
    ├── status
    ├── artifacts
    ├── evidence
    ├── findings
    └── role_specific_payload
```

Worker-supplied identity, role, task, dispatch metadata, target SHA, or runtime receipt MUST NOT override trusted context.

### 5.2 Prohibited Worker output

Workers MUST NOT return arbitrary executable Feature Events, arbitrary state patches, Gate mutations, revision mutations, or unrestricted `proposed_events`.

### 5.3 Trusted translators

Lifecycle mutations derived from Worker results MUST pass through deterministic role-specific trusted translators:

```text
Developer Result → Developer Result Translator
Reviewer Result  → Review Verdict Translator
QA Result        → Verification Verdict Translator
```

Every translator MUST validate trusted dispatch/receipt context, role-specific schema, Feature/revision/ref, task/role identity, and allowed output Event shape.

Reviewer and QA translators MUST additionally:

1. require a trusted `candidate_pr_number` and exact 40-character `candidate_head_sha` from the dispatch context;
2. verify immediately before lifecycle Persist that the canonical candidate PR still has that exact head SHA;
3. reject stale evidence/result when the head changed;
4. require a new semantic dispatch bound to the new head before new Reviewer/QA evidence can advance a Gate.

A Feature revision remaining unchanged does not make old candidate evidence reusable against a different head SHA.

## 6. Normative Operation Store

### 6.1 Trusted location

The v0.3.0 reference implementation MUST persist Operator state in the trusted control repository on a dedicated protected state ref resolved from trusted installation/control configuration, conceptually:

```text
refs/heads/ai-sdlc-operator-state
```

Target Feature branches and role workers MUST NOT receive credentials that can write this ref.

### 6.2 Append-only journal and schemas

Reference layout:

```text
state/operator/v1/
├── operations/<operation-id>/events/<sequence>-<event-id>.json
├── claims/dispatch/<dispatch-key>.json
├── claims/feature/<target-repo-hash>/<feature-id>.json
├── decisions/<decision-id>.json
├── notifications/<notification-id>.json
└── projections/<operation-id>.json
```

Operation Event schema version:

```text
ai-sdlc.operation-event/v1
```

Operation Events and consumed claim records MUST be immutable through trusted writes. Cached projections MAY be replaced but MUST be rebuildable deterministically.

### 6.3 Atomic writes

Repository-backed Operation Store updates MUST use Git ref compare-and-set:

1. read current state-ref SHA;
2. construct one bounded update from that exact tree;
3. update only if the expected ref SHA is still current;
4. on conflict, re-read and re-evaluate.

Append-only file naming alone is insufficient concurrency control.

### 6.4 Representative events

```text
operation.started
operation.resumed
operation.cancel.requested
operation.cancelled
operation.superseded
dispatch.claimed
dispatch.launch.authorized
worker.dispatched
worker.completed
worker.result.orphaned
callback.received
persist.requested
persist.linearized
persist.confirmed
operation.waiting
decision.requested
decision.responded
notification.enqueued
operation.blocked
operation.completed
operation.recovered
```

## 7. Operation generation and active ownership

For a target repository + Feature, at most one nonterminal Operation generation may own automatic progression.

`operation.start` MUST atomically claim the Feature active-operation slot. Equivalent starts return the current Operation instead of creating another owner.

Recovery takeover MUST create/increment a trusted `operation_generation` and atomically supersede the old generation. Once superseded, an old generation MUST NOT cross any later launch or Persist fence.

Generation is orchestration fencing metadata, not Feature lifecycle revision.

## 8. Semantic dispatch and immutable candidate identity

Before Worker launch, the Operator MUST claim a semantic dispatch identity containing at least:

```text
target_repository
feature_id
expected_revision
current_stage
task_identity
role
operation_generation
candidate_head_sha_when_candidate_bound
```

Reviewer/QA dispatch identity MUST include the exact candidate head SHA. A head change therefore produces a different semantic dispatch even when Feature revision and task/stage names are unchanged.

Invariant:

> For one target repository, Feature revision, stage, semantic task, role, Operation generation, and candidate head when applicable, at most one active valid Worker dispatch exists.

## 9. Launch fence and cancellation/supersession

A committed `dispatch.claimed` record is **not** sufficient authority to launch a Worker.

Immediately before creating external Worker side effects, the trusted launcher MUST perform a launch-fence check against current Operation Store state and atomically commit or validate `dispatch.launch.authorized` for the same claim.

The launch fence MUST verify:

- Feature active-operation claim still names the same Operation;
- Operation generation is still current;
- Operation is not cancelled or superseded;
- semantic dispatch claim is still active and belongs to that generation;
- trusted candidate head is still current when candidate-bound;
- any required policy/credential preconditions remain valid.

Cancellation or supersession MUST invalidate the old generation before a stale Runner can cross the launch boundary. A Runner holding an old claim MUST fail `SUPERSEDED_GENERATION` or `CANCELLED_OPERATION` and MUST NOT launch a Worker.

Required race test:

```text
Runner A commits dispatch.claimed
→ Runner B cancels/supersedes generation
→ Runner A attempts Worker launch
→ launch is rejected; no Worker side effect occurs
```

## 10. Claim-to-launch crash recovery

The dispatch protocol MUST close the crash window between claim and external Worker launch.

v0.3.0 MUST implement at least one trusted, testable mechanism that lets recovery determine whether launch occurred and safely decide whether a retry is allowed. The reference contract requires both:

1. a globally stable `external_dispatch_key` derived from trusted dispatch identity and passed to the downstream Worker runtime; and
2. a trusted launch receipt/query mechanism that can resolve that key to `NOT_LAUNCHED`, `LAUNCHED(<receipt>)`, or `UNKNOWN`.

Recovery rules:

- `NOT_LAUNCHED`: current generation may re-cross the launch fence and retry using the same external dispatch key;
- `LAUNCHED`: recovery MUST adopt/correlate the existing Worker receipt and MUST NOT launch again;
- `UNKNOWN`: fail closed as `BLOCKED`; speculative duplicate launch is forbidden.

A downstream runtime that cannot provide idempotent dispatch or authoritative receipt lookup MUST NOT be used for an automatically recoverable v0.3.0 release-slice dispatch.

Required failure injection:

```text
dispatch.claimed committed
→ Runner crashes before worker.dispatched is recorded
→ recovery queries external_dispatch_key
→ safely proves NOT_LAUNCHED or adopts existing receipt
→ no duplicate Worker side effect
```

## 11. Persist/cancel linearization

Operation cancellation and Feature lifecycle Persist cross two durable state domains, so v0.3.0 defines an explicit Persist linearization point.

### 11.1 Persist reservation

Before invoking the final Feature lifecycle write, the trusted collector MUST atomically validate the current active Operation generation and record `persist.requested` in the Operation Store with:

- operation/generation;
- dispatch/result identity;
- expected Feature revision;
- target ref;
- candidate head SHA when applicable;
- intended bounded translator outcome/Event identity.

### 11.2 Linearization point

Immediately before the Feature CAS/write, trusted Persist MUST revalidate the same operation generation/cancel fence and candidate head (when applicable).

The linearization point is the successful trusted precondition check that authorizes the exact Feature Event write against the exact expected Feature revision and exact Operation generation. This MUST be recorded as `persist.linearized` or an equivalently durable receipt correlated to the Feature Event identity.

Rules:

- if cancellation/supersession is durable **before** the Persist linearization point, the lifecycle write MUST NOT occur;
- once the exact Persist has crossed the linearization point, a later `operation.cancel` does not roll back or invalidate that already-authorized Feature write;
- after the Feature write succeeds, `persist.confirmed` records the durable Feature/Event receipt;
- if acknowledgement is lost, recovery queries Feature/Event receipts before retrying.

`operation.cancel` MUST therefore report whether an in-flight Persist had already crossed the linearization point. It stops future automatic progression but cannot retroactively revoke an already-linearized lifecycle mutation.

Required race tests cover cancellation at each boundary:

```text
before persist.requested
between persist.requested and persist.linearized
between persist.linearized and Feature CAS completion
after Feature CAS but before persist.confirmed
after persist.confirmed
```

## 12. Cancellation semantics

`operation.cancel` cancels automatic orchestration only; `feature.cancel` is a separate lifecycle action through existing Feature Event authority.

After cancellation is durable and before any Persist linearization point:

- no new Worker may launch;
- no new translator/Persist may begin;
- already-running Worker results may be stored only as orphaned audit evidence;
- orphaned work may be adopted only by a later current generation after reread/replan and a trusted adoption rule.

A Worker already launched remotely may finish because external execution may be non-revocable.

## 13. User-visible Operator state

```text
RUNNING
WAITING_EXTERNAL
NEEDS_USER
BLOCKED
DONE
CANCELLED
```

`WAITING_EXTERNAL` is only non-user waiting:

```text
WAITING_WORKER
WAITING_CI
WAITING_PR
WAITING_CALLBACK
```

`NEEDS_USER` includes:

```text
NEEDS_CLARIFICATION
NEEDS_AUTHORIZATION
NEEDS_ACCEPTANCE
NEEDS_CREDENTIAL_SETUP
```

`DONE` and `CANCELLED` are terminal Operation states. `BLOCKED` is a stable suspended/recoverable state.

## 14. Authorization policy and Decisions

Authorization boundaries MUST come from protected default-branch configuration, installation-level configuration, or trusted control-repository policy. Feature branches MAY tighten but MUST NOT expand authorization.

Authorization-bearing Decisions bind, as applicable, to:

```text
decision_id
decision_type
feature_id
operation_id
operation_generation
expected_revision
target_ref
candidate_head_sha
allowed_choices
trusted_policy_ref_or_digest
requested_by
requested_at
expires_at
responded_by_user
responded_via_client
responded_at
selected_choice
```

Generic user language such as `yes` has no authority until the AI client resolves a concrete pending Decision and submits an allowed choice through `decision.respond`.

Expired, consumed, stale-revision, wrong-ref, wrong-SHA, wrong-generation, or policy-invalid Decisions MUST be rejected.

Only minimum auditable Decision facts are persisted; full chat transcripts, secrets, and unnecessary sensitive free text MUST NOT be stored as Decision evidence.

## 15. Notification Outbox

Required notification types:

```text
decision.requested
operation.blocked
operation.completed
authorization.expiring
```

`notification.ack` may advance bounded delivery/read acknowledgement only. It MUST NOT mutate Feature lifecycle state or authorization outcomes.

Push-capable adapters MAY deliver proactively. Clients without push MUST discover unread Notifications through `operator.inbox`/`notification.list`.

## 16. Deterministic recovery matrix

| Condition | Required behavior |
|---|---|
| stale Feature revision | reread + replan |
| duplicate semantic request | return existing Operation/dispatch or idempotent success |
| duplicate callback | no duplicate side effect |
| out-of-order callback | correlate and ignore/block safely |
| PR/candidate head changes | invalidate old Reviewer/QA result; new head-bound dispatch required |
| claim committed, launch status known absent | retry same external dispatch key after current launch fence |
| claim committed, launch receipt exists | adopt existing Worker; never relaunch |
| claim committed, launch status unknown | BLOCKED; no speculative relaunch |
| Worker timeout/failure | bounded policy retry/remediation/BLOCKED |
| Reviewer REWORK | durable Developer remediation + fresh independent re-review |
| Persist response lost | query exact Feature Event/receipt before retry |
| cancellation before Persist linearization | reject lifecycle write |
| cancellation after Persist linearization | exact in-flight write may complete; no later progression |
| AI client closes | no effect on durable Operation |
| concurrent resume | Operation generation + CAS + dispatch/launch fences prevent duplicate effects |

Recovery MUST fail closed when durable evidence cannot determine a safe next action.

## 17. Acceptance boundary

Under default `standard-feature` policy, AI/Product agents MAY produce an Acceptance Recommendation but MUST NOT synthesize Human/Product Acceptance Evidence.

Default flow:

```text
AI/Product recommendation
→ NEEDS_USER / NEEDS_ACCEPTANCE
→ Human/Product Decision
→ Acceptance evidence
```

Automated low-risk acceptance profiles are outside the default v0.3.0 proof.

- Git ref CAS;
- active-operation generation claim;
- semantic dispatch claim;
- launch fence;
- external dispatch key + launch receipt lookup;
- candidate SHA binding;

### C. Operator vertical loop

Deliver:

```text
Implementation-ready Feature
→ Developer
→ independent Reviewer
→ remediation
→ independent Re-review
→ QA
→ NEEDS_USER / DONE
```

Reuse existing Commander/Router/Event/Persist and current autonomous Reviewer/QA candidate binding; do not fork lifecycle logic.

### D. Recovery, concurrency, cancellation, and Persist linearization

Deliver deterministic tests and implementation for generation fencing, launch races, claim-to-launch crash recovery, candidate-head races, Persist acknowledgement loss, and cancel/Persist linearization.

### E. Decision, authorization, notification

Deliver bounded Decisions, trusted authorization policy resolution, `operation.cancel` vs `feature.cancel`, Notification Outbox, and new-session discovery.

### F. Planning-manifest validation

`release/v0.3.0-draft.yaml` MUST have deterministic schema/validator coverage wired into repository CI before implementation Features depend on it as a machine-readable release contract.

## 19. Required tests

### 19.1 Tool/API contract

- exact API version negotiation;
- capability discovery;
- schema validation;
- structured error codes;
- idempotency;
- expected-revision rejection;
- unsupported capability/version behavior;
- `operator.inbox` discovery without prior Operation id.

### 19.2 Two-AI-client conformance

Both supported AI client adapters MUST pass the canonical common subset and identity/error/version semantics. At least one MUST perform the release-slice writes end-to-end.

### 19.3 Authorization adversarial

- Feature policy expansion rejected;
- broader credential scope rejected;
- Developer Gate PASS rejected;
- Reviewer/QA prohibited source write rejected;
- stale/wrong-ref/wrong-SHA/wrong-generation authorization replay rejected;
- expired Decision rejected.

### 19.4 Operation and callback replay

- duplicate callback;
- callback out of order;
- duplicate Worker completion;
- concurrent Operation start/resume;
- two Runners race same semantic dispatch;
- cached projection rebuild;
- session disappears and new session discovers work.

### 19.5 Candidate-head race

Required sequence:

```text
Reviewer/QA dispatch bound to head H1
→ candidate moves to H2 before result/Persist
→ H1 result rejected
→ no Gate advance
→ new semantic dispatch bound to H2 required
```

### 19.6 Launch-fence race

```text
dispatch.claimed
→ cancel/supersede generation
→ stale Runner attempts launch
→ launch rejected
```

### 19.7 Claim-before-launch crash

Inject process death after claim commit and before `worker.dispatched`; recover through external dispatch key/receipt lookup without duplicate Worker side effects.

### 19.8 Cancel/Persist linearization races

Exercise cancel before/after `persist.requested`, before/after `persist.linearized`, after Feature CAS with lost acknowledgement, and after `persist.confirmed`.

## 20. Required dogfood

### A. Happy path

Already-installed project reaches QA/stable completion without repeated `continue`.

### B. Review remediation

Independent Reviewer requires changes; Operator routes Developer remediation → fresh independent re-review → QA automatically.

### C. Session recovery

AI client closes while Operation is active; durable work reaches external wait/stable stop; new session discovers Operation, Decisions, and Notifications.

### D. Failure injection

At minimum: stale revision, duplicate callback, candidate-head race, cancel-after-claim-before-launch, claim-before-launch crash, concurrent resume, cancel/Persist races, and Persist acknowledgement loss.

### E. Transport matrix

Release evidence MUST include at least one external target and preserve v0.2 public/private trusted transport boundaries. Exact public/private matrix is a release decision recorded before candidate cut.

## 21. Release blockers

v0.3.0 MUST NOT be cut while any of these are unresolved:

1. Worker can carry arbitrary executable Feature Event/state mutation.
2. Worker can bypass role-specific trusted Result Translator.
3. Reviewer/QA result or dispatch is not bound to exact trusted candidate head SHA.
4. Current candidate head is not revalidated before Reviewer/QA lifecycle Persist.
5. Feature branch can expand authorization policy.
6. User authorization is not bound to exact Feature/revision/ref/head/generation as applicable.
7. One semantic task can create more than one active valid Worker dispatch.
8. More than one active Operation generation can own automatic progression for a Feature.
9. Cancellation/supersession cannot fence a stale claimed-but-not-launched Runner.
10. Claim-before-launch crash cannot be safely resolved through idempotent external dispatch/receipt lookup.
11. Unknown launch status can cause speculative duplicate Worker launch.
12. Cancel/Persist ordering lacks a deterministic linearization rule.
13. Cancellation before Persist linearization can still advance Feature lifecycle state.
14. Operation Journal is not append-only/rebuildable or trusted state writes lack CAS.
15. Duplicate callback/request can create duplicate side effects.
16. `operation.cancel` and `feature.cancel` are ambiguous.
17. Human approval is represented as `WAITING_EXTERNAL` rather than `NEEDS_USER`.
18. New session cannot discover unfinished Operations, pending Decisions, and unread Notifications.
19. Offline user prevents durable progress to stable stop.
20. Fewer than two materially independent supported AI client adapters pass canonical conformance.
21. No supported AI client adapter can execute required release-slice writes end-to-end.
22. Canonical Typed API lacks explicit versioning/capability discovery.
23. Decision persistence stores unnecessary full chat/sensitive content by default.
24. Human Acceptance Evidence can be synthesized solely from AI recommendation under default policy.
25. `release/v0.3.0-draft.yaml` lacks deterministic CI validation before implementation depends on it.
26. Existing v0.2 lifecycle authority, Event validation, revision CAS, candidate binding, or independent Gate guarantees regress.

## 22. Explicitly deferred from v0.3.0

- Product/Requirement/Architecture/Design full automation;
- automatic Project Takeover/install/upgrade;
- custom Web Dashboard;
- organization portfolio orchestration;
- complex central multi-repository scheduling;
- dynamic provider-cost optimization;
- automatic production deployment;
- unaudited high-risk Gate automation.

## 23. Release completion definition

v0.3.0 is complete when two supported, materially independent AI client adapters conform to the same canonical Typed API; at least one can drive the required write slice; and a real Feature can progress through Developer → independent Review → remediation/re-review → QA across chat-session interruption while candidate evidence, dispatch, cancellation, external launch, and Feature Persist remain deterministically fenced and auditable.

Release narrative:

> Users express intent. AI operates the workflow. AI-SDLC enforces policy. Independent workers perform bounded work. GitHub preserves the durable facts.
