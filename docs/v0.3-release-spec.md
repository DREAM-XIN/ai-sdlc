# AI-SDLC v0.3 release specification

Status: Review Draft

Tracking issue: #205

This document defines the implementable release boundary for AI-SDLC `0.3.0`. The broader product direction is described in `docs/v0.3-product-vision.md`.

## 1. Release objective

v0.3.0 must prove that an AI client can operate an already-installed AI-SDLC Feature through a durable, typed, recoverable orchestration layer without moving lifecycle authority into the model or worker.

The required vertical slice is:

```text
Installed project
→ AI client capability discovery / status
→ start or resume durable Operation
→ Developer
→ Independent Reviewer
→ Remediation when required
→ Independent Re-review
→ QA
→ NEEDS_USER / DONE
```

Normal progression through this slice must not require the user to repeatedly send `continue`.

Full Requirement/Design automation and Project Takeover are not release blockers for `0.3.0`; they are eligible v0.3.x follow-up work after the vertical loop is stable.

## 2. Non-negotiable authority model

v0.3.0 must preserve the lifecycle authority model established by earlier releases.

### 2.1 Operator authority

The Operator MAY:

- inspect durable project and Feature state;
- invoke the canonical typed API;
- request Commander/Router planning;
- claim one bounded semantic dispatch;
- dispatch an allowed role worker;
- collect a structured Worker Result;
- invoke a trusted role-specific Result Translator;
- request Event validation/Persist through existing trusted lifecycle paths;
- wait for external work;
- resume after callbacks;
- perform deterministic recovery;
- create Decision and Notification records;
- present a user-friendly projection.

The Operator MUST NOT:

- directly modify an authoritative Feature Manifest;
- construct arbitrary lifecycle state changes outside trusted translators;
- PASS or waive a Gate;
- override revision checks;
- treat chat state as authoritative;
- merge protected branches without exact authorization;
- expand trusted authorization policy;
- collapse independent Developer, Reviewer and QA authority into one execution identity.

### 2.2 No second Feature truth

Operator persistence MAY contain operation identity, append-only orchestration events, dispatch claims, waiting references, retries, callbacks and decisions.

Operator persistence MUST NOT become authoritative for:

- current Feature stage;
- lifecycle artifact status;
- Gate status;
- Feature revision;
- release authority.

All such facts MUST be re-derived from authoritative AI-SDLC state when making lifecycle decisions.

## 3. Canonical typed API

The canonical Operator API MUST be transport-independent. MCP is an adapter over that API, not the API definition itself.

### 3.1 Versioning

Every request and response MUST be associated with a stable API version. The initial version SHOULD use a namespace comparable to:

```text
ai-sdlc.operator/v1
```

Backward-incompatible contract changes MUST require a new API version.

### 3.2 Capability discovery

The API MUST provide capability discovery so clients do not guess available operations.

Minimum capability categories for v0.3.0:

```text
system.capabilities
project.inspect
feature.status
operation.start
operation.status
operation.resume
operation.cancel
decision.list
decision.respond
notification.list
```

If a capability is unavailable due to runtime, policy, installation or client constraints, the API MUST return that fact explicitly.

### 3.3 Write contract

Every semantic write MUST carry or derive:

- target repository identity;
- Feature id where applicable;
- operation id where applicable;
- expected Feature revision where lifecycle-sensitive;
- idempotency key;
- authenticated actor/client identity;
- requested capability;
- authorization context.

Lifecycle-sensitive calls MUST fail closed when expected revision no longer matches, then return enough structured information for safe reread/replan.

### 3.4 Error model

Errors MUST distinguish at least:

```text
INVALID_REQUEST
CAPABILITY_UNAVAILABLE
UNAUTHORIZED
POLICY_DENIED
STALE_REVISION
ALREADY_CLAIMED
ALREADY_APPLIED
EXTERNAL_WAIT
NEEDS_USER
BLOCKED
TRANSIENT_FAILURE
INTERNAL_FAILURE
```

Clients MUST NOT need to parse human text to determine retry or user-action semantics.

## 4. MCP adapter

v0.3.0 MUST provide an MCP adapter for the canonical API.

The first adapter slice SHOULD start read-only so actual AI clients can dogfood:

```text
system.capabilities
project.inspect
feature.status
operation.status
decision.list
notification.list
```

Write capabilities may be enabled incrementally only after the underlying canonical contract and authority checks are implemented.

The MCP adapter MUST NOT expose lower-level arbitrary Manifest, Event or shell mutation tools as substitutes for typed lifecycle operations.

## 5. Common Worker Result Envelope and trusted translation

v0.3.0 MUST reuse existing role-specific task/result concepts rather than replace them with one untyped generic payload.

### 5.1 Common envelope

A common Worker Result envelope MAY standardize:

```text
identity
role
task
status
artifacts
evidence
findings
role_specific_payload
execution_metadata
```

Role-specific payloads remain separately validated schemas.

Relevant roles include the existing lifecycle capabilities such as Orchestrator, Developer, Reviewer and QA. v0.3.0 release scope requires Developer, independent Reviewer and QA support; broader role coverage is v0.3.x work.

### 5.2 Prohibited worker output

A Worker Result MUST NOT contain an arbitrary executable Feature Event, arbitrary state patch, Gate mutation or revision mutation.

Fields equivalent to unrestricted `proposed_events` are forbidden.

### 5.3 Trusted translators

Lifecycle mutations derived from Worker Results MUST be produced by trusted, role-specific translators with a bounded output contract.

Required release-slice translators include conceptually:

```text
Developer Result
  → Developer Result Translator
  → bounded implementation lifecycle Event

Reviewer Result
  → Review Verdict Translator
  → bounded review/remediation lifecycle Event

QA Result
  → Verification Verdict Translator
  → bounded verification lifecycle Event
```

A translator MUST:

- verify expected role and task identity;
- validate result schema;
- bind result to expected Feature/revision/ref;
- reject stale or mismatched results;
- emit only Event shapes allowed for that role/task;
- preserve existing Event validation and Persist authority.

## 6. Durable Operation Journal

The v0.3.0 Operator MUST have a formally defined durable orchestration store.

### 6.1 Storage authority

The normative store for v0.3.0 SHOULD live in the trusted control plane rather than a mutable Feature branch.

Feature workers and Feature branches MUST NOT have write authority to Operation Journal records.

The implementation MAY use repository-backed trusted storage for v0.3.0. An external durable store is not required by this release as long as the same authority, append-only, concurrency and recovery guarantees are met.

### 6.2 Append-only event model

Operation durability MUST be represented as append-only Operation Events with deterministic projection rather than one mutable snapshot being the sole truth.

Representative Operation Events include:

```text
operation.started
dispatch.claimed
worker.dispatched
worker.completed
callback.received
persist.requested
persist.confirmed
operation.waiting
operation.resumed
decision.requested
decision.responded
notification.enqueued
operation.blocked
operation.completed
operation.cancelled
operation.recovered
```

A mutable cached projection MAY exist for performance, but it MUST be rebuildable from the journal.

### 6.3 Writer authority

Only trusted Operator/Collector/Recovery components MAY append Operation Events.

Role workers MUST NOT write Operation Journal events directly.

### 6.4 Callback correlation

Every asynchronous callback MUST carry or resolve durable correlation including:

- operation id;
- semantic dispatch id / task id;
- target repository;
- Feature id;
- expected revision or dispatch generation;
- trusted runtime execution/receipt identity.

Unknown, stale or already-consumed callbacks MUST fail safely.

### 6.5 Operation completion and retention

Operations reach terminal orchestration states:

```text
DONE
CANCELLED
BLOCKED
```

`BLOCKED` may later be explicitly recovered into a new or resumed operation when policy permits.

Retention policy MAY be implementation-configurable, but records needed for active Features, outstanding Decisions, audit correlation or unresolved retries MUST NOT be deleted.

### 6.6 Rebuild requirement

Loss of a cached Operation projection MUST be recoverable from the append-only Operation Journal.

Loss of the entire Operation Journal MUST NOT corrupt Feature lifecycle authority. A safe recovery path MUST be able to inspect authoritative Feature state plus durable PR/CI/Worker/Event receipts and either reconstruct a new operation or stop `BLOCKED` without guessing lifecycle state.

## 7. Semantic dispatch uniqueness

Feature revision CAS alone is insufficient because duplicate workers can cause side effects before lifecycle persistence.

Before launching a worker, the trusted Operator MUST claim a semantic dispatch identity.

The identity MUST bind enough fields to ensure that one semantic lifecycle task at one Feature state cannot have two simultaneously valid dispatches. The implementation SHOULD include at least:

```text
feature_id
expected_revision
current_stage
task identity
role
```

Equivalent retries of the same semantic action MUST resolve to the same dispatch claim or be rejected as `ALREADY_CLAIMED`.

The invariant is:

> For one Feature, revision, stage and semantic task, at most one active valid Worker dispatch may exist.

The system MUST test concurrent Runner attempts before Worker launch, not only duplicate Persist afterward.

## 8. Operator execution model

v0.3.0 MUST use durable short executions plus event-driven resume.

The release MUST NOT depend on one long-lived chat process or an indefinitely running workflow loop.

Typical flow:

```text
Operator execution
→ re-read authoritative state
→ Plan
→ claim dispatch
→ dispatch Worker
→ record WAITING_EXTERNAL
→ execution ends

Worker / CI callback
→ trusted collector
→ correlate operation + dispatch
→ record result / Persist as appropriate
→ trigger resume
→ re-read authoritative state
→ Plan again
```

Closing the AI client session MUST NOT cancel an active durable Operation.

## 9. Operator state projection

The user-facing top-level states are:

```text
RUNNING
WAITING_EXTERNAL
NEEDS_USER
BLOCKED
DONE
CANCELLED
```

`WAITING_EXTERNAL` MUST include only non-user waits such as:

```text
WAITING_WORKER
WAITING_CI
WAITING_PR
WAITING_CALLBACK
```

User interaction belongs under `NEEDS_USER`, including:

```text
NEEDS_CLARIFICATION
NEEDS_AUTHORIZATION
NEEDS_ACCEPTANCE
NEEDS_CREDENTIAL_SETUP
```

A user authorization MUST NOT be represented as `WAITING_EXTERNAL`.

## 10. Authorization policy

Authorization policy MUST NOT be controlled by the current Feature branch.

### 10.1 Policy sources

Ordinary engineering context MAY come from Project Adapter data, subject to the trusted baseline.

Authorization boundaries MUST come from one or more trusted sources:

- protected default-branch configuration;
- installation-level configuration;
- trusted control-repository policy.

### 10.2 Feature branch rule

A Feature branch MAY tighten its authorization envelope.

A Feature branch MUST NOT expand permissions relative to trusted baseline policy.

Attempted expansion MUST fail closed.

### 10.3 Policy changes

Changes to authorization policy itself MUST follow an independently reviewed trusted path. A Feature being governed by a policy change MUST NOT be able to approve that change for itself.

## 11. Decision model

Broad operations such as `feature.approve` are forbidden because natural-language consent is ambiguous.

The canonical contract SHOULD instead use concrete operations such as:

```text
decision.respond
merge.authorize
operation.cancel
feature.cancel
```

`operation.cancel` and `feature.cancel` are semantically distinct. Cancelling the current Operator execution MUST NOT automatically cancel the Feature.

### 11.1 Decision binding

An authorization-bearing Decision MUST bind to the exact object being approved, including as applicable:

```text
decision_id
decision_type
feature_id
operation_id
expected_revision
target_ref
candidate_head_sha
allowed_choices
requested_by
requested_at
expires_at
status
responded_by
responded_at
selected_choice
```

A generic user statement such as `yes` MUST only satisfy a Decision after the client resolves the concrete pending Decision and submits an allowed choice through `decision.respond`.

Expired, stale-revision, wrong-ref or wrong-SHA decisions MUST NOT authorize the operation.

### 11.2 Data minimization

Decision persistence MUST store only the minimum auditable decision facts.

Full conversation transcripts, unnecessary prompts, secrets and sensitive free-form content MUST NOT be persisted merely to prove a Decision.

## 12. Notification Outbox

v0.3.0 MUST provide a durable Notification Outbox for user-relevant asynchronous state changes.

Minimum notification types:

```text
decision.requested
operation.blocked
operation.completed
authorization.expiring
```

Notifications SHOULD support states comparable to:

```text
PENDING
DELIVERED
READ
EXPIRED
```

A client adapter that supports push MAY deliver proactively.

A client without push MUST be able to query unread notifications, pending Decisions and unfinished Operations at the start of a new session.

Notification failure MUST NOT alter lifecycle authority or silently convert `NEEDS_USER` into progress.

## 13. Recovery contract

Recovery SHOULD be deterministic and policy-driven rather than delegated to free-form model judgment.

Minimum required cases:

| Condition | Required behavior |
|---|---|
| stale Feature revision | re-read + replan |
| duplicate semantic request | return existing operation/dispatch or idempotent success |
| duplicate Event | no duplicate lifecycle transition |
| duplicate callback | no duplicate side effect |
| callback out of order | correlate and ignore/block safely |
| Worker timeout | bounded retry or BLOCKED by policy |
| Worker failure | classify; retry/remediate/block by policy |
| CI failure | remediation path when lifecycle permits |
| Reviewer requests changes | durable Developer remediation + independent re-review |
| PR head changes | invalidate stale result/evidence tied to old head |
| Persist response lost | query durable Event/receipt before retry |
| Event applied but acknowledgement lost | detect already-applied outcome |
| permission/credential missing | NEEDS_USER / NEEDS_CREDENTIAL_SETUP |
| AI client closes | no impact on durable operation |
| two Operators resume concurrently | dispatch claim + journal concurrency prevents duplicate launch |

Recovery MUST fail closed when the safe next action cannot be determined from durable facts.

## 14. Acceptance boundary

For the default standard Feature policy, AI/Product agents MAY produce an Acceptance Recommendation.

They MUST NOT synthesize Human/Product Acceptance Evidence merely because the AI recommends PASS.

Default behavior should be conceptually:

```text
AI/Product Acceptance Recommendation
        ↓
NEEDS_USER / NEEDS_ACCEPTANCE
        ↓
Human/Product Decision
        ↓
Acceptance / release evidence
```

Future profiles MAY define policy-automated acceptance for bounded low-risk cases, but that is outside the default v0.3.0 release proof.

## 15. v0.3.0 implementation workstreams

The release is organized around five required workstreams.

### A. Canonical API + MCP read-only adapter

Deliver:

- API versioning;
- capability discovery;
- structured errors;
- request identity/idempotency contract;
- read-only MCP surface for real-client dogfood;
- schema/contract tests.

### B. Durable Operation Journal

Deliver:

- append-only event schema;
- deterministic projection;
- trusted writer boundary;
- semantic dispatch claims;
- callback correlation;
- operation recovery primitives.

### C. Operator vertical loop

Deliver the required lifecycle slice:

```text
Implementation-ready Feature
→ Developer
→ independent Reviewer
→ remediation
→ independent Re-review
→ QA
→ NEEDS_USER / DONE
```

This workstream MUST reuse existing Commander/Router/Event/Persist and existing reviewer/QA autonomy rather than fork equivalent lifecycle logic.

### D. Recovery and concurrency

Deliver deterministic recovery for the cases in section 13, including replay and concurrent-resume tests.

### E. Decision, authorization and notification

Deliver:

- concrete Decision schema;
- `decision.respond`;
- operation-vs-Feature cancellation separation;
- trusted authorization policy resolution;
- Notification Outbox;
- new-session discovery.

## 16. Explicitly deferred from v0.3.0

The following are not required to publish `0.3.0`:

- full Product/Requirement/Architecture/Design lifecycle automation;
- automatic Project Takeover from an uninstalled repository;
- project upgrade automation;
- custom Web Dashboard;
- organization-wide portfolio orchestration;
- complex multi-repository central scheduling;
- dynamic provider cost optimization;
- automatic production deployment;
- unaudited high-risk Gate automation.

These may proceed in v0.3.x or later without weakening the v0.3.0 core invariants.

## 17. Test requirements

### 17.1 Tool schema contract tests

Must cover:

- API version negotiation;
- capability discovery;
- valid/invalid schemas;
- stable structured error codes;
- idempotency behavior;
- expected-revision rejection;
- unsupported capability handling.

### 17.2 Authorization adversarial tests

Must cover attempts where:

- Feature branch expands merge policy;
- Feature branch requests broader credential scope;
- Developer attempts Gate PASS;
- Reviewer attempts prohibited source mutation through Operator capability;
- stale authorization is replayed after revision change;
- authorization is replayed for a different target ref;
- merge authorization is replayed for a different candidate SHA;
- expired Decision is reused.

### 17.3 Callback and operation replay tests

Must cover:

- callback delivered twice;
- callbacks delivered out of order;
- Worker completion observed twice;
- two Runners attempt the same dispatch simultaneously;
- Persist succeeds but response is lost;
- cached projection is deleted and rebuilt;
- Operation resume occurs after AI client session disappearance.

### 17.4 Multi-client conformance

The canonical typed API MUST pass the same conformance scenarios through at least two materially independent AI client adapters before v0.3.0 release.

MCP may be one adapter. The second adapter must exercise the same canonical semantics through another supported client integration path rather than duplicating the same adapter implementation under a different name.

## 18. Required dogfood matrix

v0.3.0 release evidence must include at least:

### Scenario A: happy path

An already-installed project enters the vertical loop and reaches QA / stable completion without repeated user `continue` messages.

### Scenario B: review remediation

Independent Reviewer returns a change-requiring finding. Operator creates/dispatches Developer remediation, then triggers independent re-review and proceeds to QA without user lifecycle driving.

### Scenario C: session recovery

The AI client session is terminated while the Operation is active. Durable execution proceeds to an external wait or stable stop. A new session discovers the unfinished/completed Operation and relevant unread notifications/decisions.

### Scenario D: failure injection

At least stale revision, duplicate callback, concurrent resume and Persist-acknowledgement-loss paths are exercised without duplicate lifecycle or worker side effects.

### Scenario E: public/private transport

The required vertical loop must be dogfooded across the release-selected target matrix, including at least one external target and preserving v0.2 public/private trusted transport boundaries. The exact matrix is a release decision and must be recorded in `release/v0.3.0-draft.yaml` before candidate cut.

## 19. Release blockers

`0.3.0` MUST NOT be cut while any of the following are unresolved:

1. Worker Result can carry arbitrary executable Feature Event/state mutation.
2. A Worker can bypass its role-specific trusted Result Translator.
3. User authorization is not bound to exact Feature/revision/ref and candidate SHA when applicable.
4. Feature branch can expand its own authorization policy.
5. One semantic task at one Feature revision/stage can create more than one active valid Worker dispatch.
6. Operation Journal is not append-only or its projection cannot be rebuilt deterministically.
7. Loss of cached Operation state can leave the Feature irrecoverable.
8. Duplicate callback/request can produce duplicate side effects.
9. `operation.cancel` and `feature.cancel` are not distinct.
10. `WAITING_APPROVAL` or equivalent is treated as a non-user external wait.
11. New sessions cannot discover unfinished Operations, pending Decisions and unread Notifications.
12. Offline users prevent durable progress to a stable stop condition.
13. After initial installation authorization, a normal release-slice Feature requires routine manual GitHub operations.
14. Typed API lacks explicit versioning or capability discovery.
15. Typed API fails conformance on two independent AI client adapters.
16. Decision persistence stores unnecessary full chat/sensitive content by default.
17. Human Acceptance Evidence can be synthesized solely from an AI recommendation under default policy.
18. Current v0.2 lifecycle authority, Event validation, revision CAS or independent Gate guarantees are weakened.

## 20. Release completion definition

v0.3.0 is complete when a user can use a supported AI client to inspect and operate the required Feature slice through the typed Operator surface, leave the session, return later from a new session, and observe a correct durable result without learning or manually manipulating internal AI-SDLC protocol state.

The release narrative is:

> Users express intent. AI operates the workflow. AI-SDLC enforces policy. Independent workers perform bounded work. GitHub preserves the durable facts.
