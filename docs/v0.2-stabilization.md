# AI-SDLC v0.2 stabilization baseline

This document defines the stabilization boundary for the next AI-SDLC baseline after `0.1.0`.

The purpose of v0.2 is not to redesign lifecycle semantics. It is to make the already-proven autonomous and cross-repository execution paths repeatable, observable, least-privilege, and releaseable across materially different target repositories.

## Proven capabilities

The following capabilities are already implemented on `main` and are treated as part of the v0.2 candidate surface:

- provider-neutral Commander and Runtime Router boundaries;
- autonomous `gh-aw` execution with bounded Safe Output Draft PR creation;
- Feature-specific execution context propagation, including linked Feature Issue context;
- durable review remediation tasks without reopening completed work stages;
- trusted Issue Comment command transport for Bootstrap, Plan, Persist, and autonomous dispatch;
- artifact registration and approval through Feature Events;
- cross-repository autonomous handoff into private target repositories;
- deterministic cross-repository dispatch identity, duplicate suppression, and exact receipt correlation;
- least-privilege Runtime GitHub App delegation scoped to the exact target repository;
- provider-neutral Runtime App installation preflight;
- target-installation contract preflight before the first Feature, covering Project Adapter schema/semantics, required context, `AGENTS.md`, repository identity, command working directories, and immutable caller pins;
- workflow-profile-aware Commander task context, including executable `small-change` requirement/implementation/review/verification contracts without nonexistent design/plan dependencies;
- compiled-worker allowlisting at the low-level autonomous gateway;
- current-main Gemini worker materialization with Gemini CLI `0.52.0` and all-engine strict compile validation;
- full external Feature lifecycle dogfood through requirement, design, implementation, review, verification, acceptance, and release Gate completion.

## v0.1 -> v0.2 capability increment

v0.1 established the durable protocol, deterministic control plane, manual runtime contract, Project Adapter, Feature Events, Gate/Evidence semantics, and a reference autonomous runtime.

v0.2 stabilizes the execution layer around that protocol:

1. **Autonomous Feature context** — workers receive concrete Feature-specific outputs and linked Issue context instead of relying on generic role prompts.
2. **PR lifecycle automation** — review and verification evidence can be collected into Feature state without manually authoring Event YAML for normal PR flows.
3. **Review remediation** — `CHANGES_REQUESTED` can create durable remediation tasks and replay the original implementation role without granting the worker review or Gate authority.
4. **Provider/runtime separation** — runtime, provider, and model selection remain outside lifecycle authority, with effective model metadata made auditable.
5. **Cross-repository command transport** — target repositories can invoke trusted control-plane operations without copying lifecycle logic.
6. **Cross-repository autonomous execution** — the trusted control repository can execute bounded work against a private target repository and return results through the existing Feature Event/Persist path.
7. **Idempotent dispatch and receipts** — semantic dispatch identities prevent duplicate autonomous side effects and correlate command receipts to exact downstream runs.
8. **Two-layer installation preflight** — target repositories can validate their durable Project Adapter/context/caller contract before a Feature exists, while the separate Runtime App preflight validates exact-target autonomous access.
9. **Profile-aware task contracts** — Commander task requirements are resolved against the active Workflow Profile rather than assuming every Feature contains standard-feature design/plan stages.
10. **Reproducible provider engines** — generated provider workers retain current control-plane semantics while pinning independently validated engine versions such as Gemini CLI `0.52.0`.

## Current stabilization blockers

### Feature-context dogfood

The Feature-context dogfood remains an explicit v0.2 blocker. Its current bounded remediation has the correct one-file scope and runtime metadata, and the content-side review has been approved.

Repository validation is still waiting for a normal green job result. The release baseline must not substitute a manual Gate override or content-only review for the explicit green-CI acceptance criterion. The Feature must still complete its normal review/verification lifecycle after that external Actions approval condition is cleared.

### Repeated cross-repository dogfood

The generic installation path is installed and proven across two materially different private target repositories. Dedicated **AI-SDLC Installation Check** runs passed in both targets using the merged generic target-installation preflight.

The remaining work is lifecycle completion, not installation plumbing.

#### Private candidate A

A desktop/mobile TypeScript target reached independent review with requirement and implementation complete.

Proven implementation evidence includes:

- repository formatting failures were repaired without changing runtime logic;
- the next CI layer correctly exposed missing native Linux build prerequisites;
- the target's existing validation chain was kept unchanged;
- the repaired implementation passed formatting, type checks, tests, and native desktop-shell compilation;
- durable implementation verification evidence is registered.

The Feature is intentionally parked before its code Gate: independent review and verification must still occur. The implementation author must not approve the same Feature's independent review Gate.

#### Private candidate B

A Java/Vue security-sensitive target correctly failed closed during a low-risk CI-baseline Feature after repository tooling repairs exposed a pre-existing cryptographic API compatibility problem.

Because the affected path is security- and encrypted-data-compatibility-sensitive, the low-risk Feature did not opportunistically change cryptographic behavior or dependencies. The work was split into a high-risk standard Feature whose requirement makes cryptographic parameters, output size, authenticated-encryption invariants, cross-implementation compatibility evidence, and backward-compatibility analysis explicit. Independent requirement review must complete before design or implementation.

## Reconciled legacy generated runtime work

A stale generated-runtime PR was not merged from its old branch. Its unresolved Gemini CLI `0.52.0` goal was rematerialized from current `main` via the supported materializer.

The current-main rematerialization inherited the current cross-repository worker contract, generated the Gemini source/lock with `@google/gemini-cli@0.52.0`, passed protocol/cross-repository validation and the all-engine strict compile matrix, and then merged. The stale PR is therefore superseded rather than merged as-is.

## Release baseline policy

A formal v0.2 release candidate should be cut only after:

- the Feature-context dogfood is fully closed with green validation evidence;
- both repeated cross-repository dogfoods complete through their required independent review/verification Gates, or an explicit release decision narrows the required matrix;
- README and release documentation describe the implemented architecture and current blockers;
- the machine-readable v0.2 release manifest contains only capabilities and validators present on the release commit;
- `VERSION` is changed from `0.1.0` only in the final reviewed release-baseline change, not during stabilization.

The stale generated-runtime blocker is already reconciled through current-main rematerialization and is no longer a release blocker.

## Scope control

Do not add one-shot Feature-specific recovery workflows to satisfy this baseline. A new dogfood failure must either:

- be resolved through an existing generic recovery/remediation mechanism; or
- become a generic control-plane capability with deterministic validation and documented authority boundaries.

Feature-specific workarounds are evidence of a missing reusable capability, not release completion.
