# AI-SDLC v0.3 release specification

Status: Review Draft — re-review required

Tracking issue: #205

Superseded review baseline: `ecad1c42d04c3212376e3baade4f1905d5aed384`

This document defines the implementable release boundary for AI-SDLC `0.3.0`. The broader product direction remains in `docs/v0.3-product-vision.md`.

## 1. Release objective

v0.3.0 proves that supported AI clients can operate an already-installed AI-SDLC Feature through a durable, typed, recoverable Operator without moving lifecycle authority into the model, worker, client session, or Operator store.

Required vertical slice:

```text
Installed project
→ AI client capability/status/inbox
→ start or discover durable Operation
→ Developer
→ Independent Reviewer
→ Remediation when required
→ Independent Re-review
→ QA
→ NEEDS_USER / DONE
```

Normal progression through this slice MUST NOT require repeated user `continue` messages.

Full Requirement/Design automation and Project Takeover are deferred to v0.3.x and MUST NOT block v0.3.0.

## 2. Authority invariants

The Operator MAY inspect state, plan, claim bounded work, dispatch role workers, collect results, invoke trusted translators, request existing Feature Event/Persist paths, recover deterministic failures, and create bounded Decision/Notification records.

The Operator MUST NOT:

- directly edit authoritative Feature Manifests;
- construct arbitrary lifecycle mutations outside trusted translators;
- PASS or waive Gates on its own authority;
- override optimistic revision checks;
- treat chat or Operator projection state as Feature authority;
- broaden authorization policy;
- merge protected branches without exact authorization;
- collapse Developer, Reviewer and QA into one execution identity.

Feature lifecycle truth remains derived from authoritative AI-SDLC state. Operation state is orchestration metadata only.

## 3. Canonical Typed API

### 3.1 Version

The canonical API identifier for v0.3.0 is:

```text
ai-sdlc.operator/v1
```

Every request and response MUST identify the API version. `system.capabilities` MUST return supported API versions and capabilities. Unsupported versions MUST fail as `UNSUPPORTED_API_VERSION` without executing semantic writes.

Backward-incompatible changes require a new canonical API version.

### 3.2 Required capabilities

```text
system.capabilities
project.inspect
feature.status
operator.inbox
operation.start
operation.status
operation.resume
operation.cancel
decision.list
decision.respond
notification.list
notification.ack
```

`operator.inbox` is the new-session discovery primitive. An authorized client MUST be able to discover unfinished Operations, `NEEDS_USER`/`BLOCKED` Operations, pending Decisions, and unread Notifications without knowing an `operation_id` from a prior chat.

Routine `WAITING_EXTERNAL` callbacks resume automatically. `operation.resume` is reserved for explicit policy-permitted recovery from a suspended state such as `BLOCKED`.

### 3.3 Identity and semantic writes

Authenticated calls MUST distinguish:

- human principal when represented;
- AI client adapter identity;
- trusted service/runtime identity;
- requested capability.

AI client identity MUST NOT itself imply human authorization.

Every semantic write MUST carry or derive:

- target repository;
- Feature id where applicable;
- Operation id/generation where applicable;
- expected Feature revision where lifecycle-sensitive;
- idempotency key;
- authenticated identities;
- requested capability;
- trusted authorization-policy context.

### 3.4 Error model

Clients MUST receive structured errors rather than parse human text. Minimum errors:

```text
INVALID_REQUEST
UNSUPPORTED_API_VERSION
CAPABILITY_UNAVAILABLE
UNAUTHORIZED
POLICY_DENIED
STALE_REVISION
ALREADY_CLAIMED
ALREADY_APPLIED
SUPERSEDED_GENERATION
CANCELLED_OPERATION
EXTERNAL_WAIT
NEEDS_USER
BLOCKED
TRANSIENT_FAILURE
INTERNAL_FAILURE
```

## 4. AI Client adapters and conformance

v0.3.0 MUST ship at least two materially independent, supported **AI client adapters** over the canonical API. MCP MAY be one adapter.

Both AI client adapters MUST pass the same canonical conformance subset:

```text
system.capabilities
feature.status
operator.inbox
operation.status
decision.list
notification.list
```

Both adapters MUST additionally prove canonical version negotiation, structured errors, identity propagation, and unsupported-capability behavior.

At least one of the two supported AI client adapters MUST execute the release-slice writes end-to-end, including as applicable:

```text
operation.start
operation.cancel
decision.respond
notification.ack
```

The second adapter MAY remain read-oriented for end-to-end dogfood, but it MUST still be a genuine supported AI client adapter that independently exercises the canonical boundary. Renaming or thinly wrapping the same adapter implementation does not count.

Adapters MUST NOT expose arbitrary Manifest/Event/shell mutation as substitutes for canonical operations.

## 5. Worker Result boundary and immutable candidate binding

### 5.1 Trusted context versus Worker payload

Trusted context MUST be constructed by trusted runtime/collector code from dispatch records and execution receipts. Workers MUST NOT self-assert translator-driving identity.

Conceptual envelope:

```text
Trusted Result Envelope
├── trusted_context
│   ├── operation_id
│   ├── operation_generation
│   ├── semantic_effect_key
│   ├── external_dispatch_key
│   ├── dispatch_id
│   ├── target_repository
│   ├── feature_id
│   ├── expected_revision
│   ├── target_ref
│   ├── candidate_pr_number          # when candidate-bound
│   ├── candidate_head_sha           # required for Reviewer/QA
│   ├── task_id
│   ├── role
│   └── runtime_receipt_identity
└── worker_payload
    ├── status
    ├── artifacts
    ├── evidence
    ├── findings
    └── role_specific_payload
```

Worker-supplied identity, role, task, dispatch identity, candidate identity, or execution metadata MUST NOT override trusted context.

### 5.2 Prohibited Worker output

A Worker Result MUST NOT contain an arbitrary executable Feature Event, arbitrary state patch, Gate mutation, revision mutation, or unrestricted `proposed_events` equivalent.

### 5.3 Trusted translators

Lifecycle mutations derived from Worker Results MUST be produced by deterministic trusted role-specific translators:

```text
Developer Result → Developer Result Translator
Reviewer Result  → Review Verdict Translator
QA Result        → Verification Verdict Translator
```

A translator MUST:

- consume trusted dispatch/receipt context;
- validate the role-specific result schema;
- bind to expected Feature revision/ref;
- bind Reviewer/QA results to exact candidate PR/head SHA;
- reject stale or mismatched results;
- re-fetch and verify the current candidate head immediately before Persist when candidate-bound;
- emit only Event shapes allowed for the role/task;
- preserve existing Event validation and Persist authority.

If the candidate head changes, the prior result/evidence MUST NOT be rebound. A new semantic task/dispatch for the new head is required.

## 6. Normative Operation Store

v0.3.0 uses a repository-backed trusted Operation Store in the trusted control repository. It MUST NOT live on the target Feature branch.

### 6.1 Protected state ref

The reference implementation MUST persist Operator state on a dedicated protected control-plane state ref selected by trusted installation/control configuration, conceptually:

```text
refs/heads/ai-sdlc-operator-state
```

A Feature branch MUST NOT select or modify this ref. Role workers MUST NOT receive credentials that can write it.

### 6.2 Versioned append-only layout

Conceptual v1 layout:

```text
state/operator/v1/
├── operations/<operation-id>/events/<sequence>-<event-id>.json
├── reservations/external/<semantic-effect-key>.json
├── claims/dispatch/<dispatch-claim-id>.json
├── claims/feature/<target-repo-hash>/<feature-id>.json
├── decisions/<decision-id>.json
├── notifications/<notification-id>.json
└── projections/<operation-id>.json
```

Operation Event schema version:

```text
ai-sdlc.operation-event/v1
```

Operation Events and consumed reservations/claims MUST be immutable through the trusted path. Cached projections MAY be replaced but MUST be deterministically rebuildable.

### 6.3 Writer authority and CAS

Only trusted Operator/Collector/Recovery components MAY append Operation Events or mutate bounded reservation/claim/projection/Decision/Notification state.

The repository-backed implementation MUST use Git ref compare-and-set semantics:

1. read current trusted state-ref SHA;
2. construct the bounded update against that exact tree;
3. update the protected ref only if the expected ref SHA remains current;
4. on conflict, re-read and re-evaluate before retrying.

## 7. Operation generation and external semantic side-effect reservation

Operation generation and external side-effect identity are deliberately separate concepts.

### 7.1 One active Operation generation per Feature

For a given target repository and Feature, at most one nonterminal Operation generation may own automatic progression.

`operation.start` MUST atomically claim the Feature active-operation slot. Equivalent starts return the existing active Operation.

A trusted recovery takeover MAY supersede generation `G` with `G+1` only through an atomic handover that records `operation.superseded` and fences `G` from new orchestration decisions.

### 7.2 Generation-independent semantic effect key

A potential external Worker launch has a durable **semantic effect reservation** whose identity MUST NOT include Operation generation.

The semantic effect key MUST bind enough immutable facts to identify one external side effect, including at least:

```text
target_repository
feature_id
expected_revision
current_stage
task_identity
role
candidate_head_sha_when_candidate_bound
```

Conceptually:

```text
semantic_effect_key = hash(
  target_repository,
  feature_id,
  expected_revision,
  current_stage,
  task_identity,
  role,
  candidate_head_sha_when_candidate_bound
)
```

The stable `external_dispatch_key` is derived from or permanently bound to this semantic effect reservation and MUST survive Operation-generation takeover.

Operation generation identifies which orchestration owner may act on the reservation; it MUST NOT create a new external identity for the same semantic side effect.

### 7.3 Generation-specific dispatch claim

A generation-specific dispatch claim references the generation-independent semantic effect reservation.

Before launch processing, the trusted Operator MUST atomically claim ownership for the current generation. Equivalent retries resolve to the existing reservation/claim or `ALREADY_CLAIMED`.

Invariant:

> For one semantic effect key, at most one external dispatch identity may ever be valid, even if Operation ownership moves from generation G to G+1.

A new generation MAY inherit recovery responsibility for the existing reservation. It MUST NOT create a new `semantic_effect_key` or `external_dispatch_key` merely because generation changed.

## 8. Launch linearization and cancellation/supersession fencing

### 8.1 Launch preparation

Before authorizing an external launch, trusted code MUST re-read the Operation Store and authoritative Feature/candidate state and verify:

- Operation generation is current;
- Operation is not cancelled or superseded;
- generation-specific dispatch claim still owns the semantic effect reservation;
- expected Feature revision/stage remain valid;
- candidate head still matches when candidate-bound;
- trusted policy/credential preconditions remain satisfied.

### 8.2 Launch linearization point

`dispatch.launch.authorized` is the normative **launch linearization point**.

It MUST be committed durably and atomically in the trusted Operation Store against the current generation and the existing semantic effect reservation before the external launch call is attempted.

The record MUST bind at least:

```text
operation_id
operation_generation
semantic_effect_key
external_dispatch_key
dispatch_id
feature_id
expected_revision
stage
role
candidate_head_sha_when_applicable
launch_authorized_at
```

The ordering rule is:

- cancellation/supersession durable **before** `dispatch.launch.authorized` wins: launch authorization MUST fail and no external launch may occur;
- `dispatch.launch.authorized` durable **before** cancellation/supersession wins for that exact dispatch: cancellation/supersession MUST NOT retroactively revoke the already-authorized external side effect;
- cancellation after launch linearization still stops all later unlinearized work and prevents the eventual Worker result from automatically advancing lifecycle state unless a later trusted adoption/recovery rule explicitly permits it.

Therefore a stale runner that resumes after cancellation MAY perform only the exact external launch that was already launch-linearized before cancellation, using the same stable `external_dispatch_key`. It MUST NOT authorize or launch any different/new dispatch.

This is intentional distributed-system semantics: `operation.cancel` is not guaranteed to revoke a side effect that already crossed its trusted launch linearization point.

### 8.3 External runtime idempotency and launch receipt

The external Worker runtime used by the v0.3 release slice MUST support a stable external dispatch key plus trusted launch-receipt lookup, either natively or through a trusted gateway that provides equivalent semantics.

Lookup states:

```text
NOT_LAUNCHED
LAUNCHED
UNKNOWN
```

- `NOT_LAUNCHED`: the exact semantic reservation may be retried with the same external key, but only after the current generation passes the required launch authorization/fence;
- `LAUNCHED`: adopt/correlate the existing launch receipt; MUST NOT launch again;
- `UNKNOWN`: MUST NOT speculatively relaunch.

### 8.4 Claim/authorization crash recovery

If a Runner crashes after reservation/claim or after launch authorization but before a local `worker.dispatched` record, recovery MUST query the trusted launch receipt using the existing `external_dispatch_key`.

Recovery MUST NOT infer launch absence from missing local journal events.

## 9. UNKNOWN reservation inheritance across Operation generations

An unresolved external launch reservation is durable Feature-adjacent orchestration safety state, not disposable generation-local state.

If launch state is `UNKNOWN`:

1. the Operation enters or remains `BLOCKED` for that semantic effect;
2. trusted takeover MAY move Operation ownership to `G+1`;
3. the unresolved semantic effect reservation and exact `external_dispatch_key` MUST be inherited unchanged by `G+1`;
4. `G+1` MUST NOT create a new external dispatch/key for the same semantic task while the inherited reservation remains unresolved;
5. recovery continues querying/correlating the same reservation until it becomes `NOT_LAUNCHED`, `LAUNCHED`, or is safely retired by a trusted rule that proves no duplicate external side effect can result.

A generation change by itself is never sufficient to retire an `UNKNOWN` reservation.

If authoritative Feature state later makes the semantic task obsolete, late callbacks/results remain correlated to the inherited reservation and MUST be rejected/orphaned unless a bounded trusted adoption rule proves they are applicable to the new state. Obsolescence MUST NOT be implemented by silently generating a new key for the same unresolved side effect.

## 10. Operation cancellation

`operation.cancel` stops automatic progression; it is not Feature cancellation.

Cancellation MUST be durably committed in the trusted Operation Store and MUST return enough status to report any already launch-linearized or Persist-linearized work that may still complete.

After cancellation is durable:

- no new Operation decision may be linearized for that generation;
- no external Worker launch lacking a pre-existing `dispatch.launch.authorized` record may occur;
- an exact dispatch whose launch authorization linearized before cancellation MAY still be externally launched if necessary for idempotent completion/correlation;
- any later Worker result from the cancelled generation MUST be recorded for audit but MUST NOT automatically advance lifecycle state unless it had already crossed Persist linearization or is explicitly adopted by a later trusted rule;
- `feature.cancel` remains a separate existing lifecycle/Event operation.

## 11. Persist linearization

Feature lifecycle Persist has an independent linearization boundary.

Before Feature write, trusted code MUST:

1. record `persist.requested` with Operation/generation/result/Event identity;
2. re-read current Operation generation/cancel/supersession state;
3. revalidate expected Feature revision;
4. revalidate candidate head when applicable;
5. atomically commit `persist.linearized` (or equivalent durable authorization receipt) in the Operation Store;
6. only then perform the exact Feature Event/Persist write;
7. record `persist.confirmed` after durable confirmation.

Ordering rule:

- cancellation/supersession before `persist.linearized` wins and the Feature write MUST NOT occur;
- `persist.linearized` before cancellation wins for that exact Event/write, which MAY complete afterward;
- cancellation after Persist linearization prevents subsequent automatic progression but does not roll back the already-authorized Feature write;
- if Feature Persist succeeds but acknowledgement is lost, recovery MUST query the exact Event/receipt before retrying.

Launch linearization and Persist linearization are distinct. A launch-authorized Worker result does not automatically gain Persist authority.

## 12. User-visible Operator state

Top-level states:

```text
RUNNING
WAITING_EXTERNAL
NEEDS_USER
BLOCKED
DONE
CANCELLED
```

`WAITING_EXTERNAL` is non-user wait only:

```text
WAITING_WORKER
WAITING_CI
WAITING_PR
WAITING_CALLBACK
```

`NEEDS_USER` includes:

```text
NEEDS_CLARIFICATION
NEEDS_AUTHORIZATION
NEEDS_ACCEPTANCE
NEEDS_CREDENTIAL_SETUP
```

`DONE` and `CANCELLED` are terminal Operation states. `BLOCKED` is a stable suspended/recoverable state, not Feature authority.

## 13. Authorization and Decision model

Authorization policy MUST NOT be controlled by the current Feature branch.

Trusted sources:

- protected default-branch configuration;
- installation-level configuration;
- trusted control-repository policy.

A Feature branch MAY tighten permissions but MUST NOT expand them.

Authorization-bearing Decisions MUST bind, as applicable:

```text
decision_id
decision_type
feature_id
operation_id
operation_generation
expected_revision
target_ref
candidate_head_sha
allowed_choices
trusted_policy_ref_or_digest
requested_by
requested_at
expires_at
status
responded_by_user
responded_via_client
responded_at
selected_choice
```

A generic user statement such as `yes` only satisfies a Decision after the client resolves the concrete pending Decision and submits an allowed choice through `decision.respond`.

Expired, consumed, stale-revision, wrong-ref, wrong-SHA, wrong-generation, or policy-invalid Decisions MUST NOT authorize work.

Decision persistence MUST store minimum auditable facts, not full chat transcripts or secrets.

## 14. Notification Outbox

v0.3.0 MUST provide a durable Notification Outbox.

Minimum types:

```text
decision.requested
operation.blocked
operation.completed
authorization.expiring
```

`notification.ack` MAY advance bounded delivery/read acknowledgement for an authorized notification. It MUST NOT alter Feature lifecycle state or authorization outcomes.

Clients without push MUST discover unread Notifications through `operator.inbox` / `notification.list` in a new session.

## 15. Recovery contract

Recovery MUST be deterministic and policy-driven rather than free-form model judgment.

| Condition | Required behavior |
|---|---|
| stale Feature revision | re-read + replan |
| duplicate semantic request | return existing Operation/reservation or idempotent success |
| duplicate Event | no duplicate lifecycle transition |
| duplicate callback | no duplicate side effect |
| out-of-order callback | correlate and ignore/block safely |
| Reviewer/QA result for stale candidate head | reject; new candidate requires new dispatch |
| cancel/supersede before launch linearization | no launch |
| cancel/supersede after launch linearization | exact authorized launch may complete; result fenced from automatic Persist |
| crash after claim before launch | query stable external key; retry/adopt/block from receipt state |
| external launch receipt `UNKNOWN` | BLOCKED; reservation survives generation takeover; no new key |
| Worker timeout | bounded recovery or BLOCKED by policy |
| Worker failure | classify; retry/remediate/block by policy |
| CI failure | remediation path when lifecycle permits |
| PR head changes | invalidate stale candidate evidence |
| cancel before Persist linearization | no Feature write |
| cancel after Persist linearization | exact authorized Feature write may complete |
| Persist acknowledgement lost | query exact Event/receipt before retry |
| AI client closes | no effect on durable Operation |
| concurrent Operator resume | CAS + reservation + generation fencing prevents duplicate side effect |

When safe next action cannot be proven from durable facts, recovery MUST fail closed.

## 16. Acceptance boundary

Under the default standard Feature policy:

```text
AI/Product Acceptance Recommendation
        ↓
NEEDS_USER / NEEDS_ACCEPTANCE
        ↓
Human/Product Decision
        ↓
Acceptance / release evidence
```

AI recommendation alone MUST NOT synthesize Human/Product Acceptance Evidence.

## 19. Required tests

### 19.1 Tool/API contract

Must cover:

- API version negotiation;
- capability discovery;
- schema validation;
- structured error codes;
- identity propagation;
- idempotency;
- expected-revision rejection;
- unsupported capability handling.

### 19.2 Authorization adversarial

Must cover:

- Feature policy expansion rejected;
- broader credential request rejected;
- Developer Gate PASS rejected;
- Reviewer prohibited source write rejected;
- stale authorization replay rejected;
- wrong ref/SHA/generation authorization rejected;
- expired Decision rejected.

### 19.3 Candidate binding

Must cover:

```text
Reviewer/QA dispatched at candidate SHA A
→ candidate moves to SHA B
→ result for A arrives
→ translator/Persist rejects A
→ B requires new semantic dispatch
```

### 19.4 Launch linearization race

Must cover exactly:

```text
dispatch.launch.authorized for generation G
→ cancellation or supersession becomes durable
→ stale runner reaches external launch
→ exact pre-authorized external_dispatch_key may be launched/correlated
→ no new dispatch/key is created
→ eventual result cannot automatically Persist under cancelled/superseded generation
```

And the opposite ordering:

```text
cancellation or supersession durable
→ stale runner attempts dispatch.launch.authorized
→ authorization fails
→ no external launch
```

### 19.5 UNKNOWN reservation takeover

Must cover exactly:

```text
G launch receipt = UNKNOWN
→ Operation BLOCKED
→ trusted takeover to G+1
→ same semantic task
→ G+1 inherits same semantic_effect_key/external_dispatch_key
→ no new external key may be generated
→ UNKNOWN remains fail-closed until resolved
```

### 19.6 Claim/launch crash recovery

Must cover:

- reservation committed, crash before launch authorization;
- launch authorization committed, crash before external call;
- external call succeeds, local `worker.dispatched` record lost;
- lookup returns `NOT_LAUNCHED`, `LAUNCHED`, and `UNKNOWN`.

### 19.7 Persist/cancel race

Must cover cancellation at:

- before `persist.requested`;
- after `persist.requested` but before `persist.linearized`;
- after `persist.linearized` but before Feature CAS/write acknowledgement;
- after Feature write but before `persist.confirmed`.

Expected outcomes MUST follow Section 11 linearization rules.

### 19.8 Callback/operation replay

Must cover:

- duplicate callback;
- out-of-order callback;
- duplicate Worker completion;
- concurrent Runner resume;
- cached projection deletion/rebuild;
- AI client session disappearance.

### 19.9 Multi-client conformance

The same canonical conformance subset MUST pass through at least two materially independent supported AI client adapters before release.

## 21. Release blockers

`0.3.0` MUST NOT be cut while any of the following are unresolved:

1. Worker Result can carry arbitrary executable Feature mutation.
2. Worker can bypass its trusted role-specific Result Translator.
3. Reviewer/QA result/evidence is not bound to exact candidate head SHA.
4. Candidate head is not revalidated before candidate-bound Persist.
5. User authorization is not bound to exact Feature/revision/ref/SHA/generation as applicable.
6. Feature branch can expand its own authorization policy.
7. More than one active Operation generation can automatically progress one Feature.
8. Semantic external side-effect reservation identity changes merely because Operation generation changes.
9. Same semantic effect can obtain more than one external dispatch key.
10. `dispatch.launch.authorized` is not a durable launch linearization point with defined cancellation ordering.
11. Cancellation/supersession before launch linearization can still produce an external launch.
12. Cancellation/supersession after launch linearization can cause a second/different dispatch or automatically authorize Persist.
13. Claim/launch crash cannot be recovered through stable external key plus trusted launch receipt lookup.
14. `UNKNOWN` launch state can be bypassed by takeover to a new Operation generation.
15. Operation Store is not append-only/rebuildable or trusted-state-ref CAS is missing.
16. Duplicate callback/request can create duplicate lifecycle or external side effects.
17. Persist/cancel lacks explicit linearization semantics.
18. `operation.cancel` and `feature.cancel` are not distinct.
19. New sessions cannot discover unfinished Operations, pending Decisions, and unread Notifications.
20. Offline users prevent progress to stable stop.
21. Normal release-slice Feature requires routine manual GitHub operations after installation.
22. Typed API lacks exact versioning/capability discovery.
23. Fewer than two materially independent supported AI client adapters pass canonical conformance.
24. No supported AI client adapter exercises release-slice writes end-to-end.
25. Decision persistence stores unnecessary full chat/sensitive content by default.
26. Human Acceptance Evidence can be synthesized solely from AI recommendation under default policy.
27. `release/v0.3.0-draft.yaml` lacks deterministic validator coverage before implementation dependency.
28. v0.2 lifecycle authority, Event validation, revision CAS, independent Gate, or trusted transport guarantees regress.

## 22. Release completion definition

v0.3.0 is complete when supported AI clients can inspect and operate the required Feature slice through `ai-sdlc.operator/v1`, leave and re-enter sessions safely, and observe a correct durable outcome while external Worker launches and Feature Persists obey explicit linearization/fencing rules and the user never needs to manipulate internal Manifest/Event/Gate protocol state directly.

Release narrative:

> Users express intent. AI operates the workflow. AI-SDLC enforces authority. Independent workers perform bounded work. GitHub preserves durable facts.
