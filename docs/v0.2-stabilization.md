# AI-SDLC v0.2 stabilization baseline

This document defines the stabilization boundary for AI-SDLC `0.2.0`.

The purpose of v0.2 is not to redesign lifecycle semantics. It stabilizes the already-proven autonomous and cross-repository execution paths so they are repeatable, observable, least-privilege, and releaseable across materially different target repositories.

## Proven capabilities

The v0.2 candidate surface includes:

- provider-neutral Commander and Runtime Router boundaries;
- autonomous `gh-aw` execution with bounded Safe Output Draft PR creation;
- Feature-specific execution context propagation, including linked Feature Issue context;
- durable review remediation without reopening completed work stages;
- trusted Issue Comment transport for Bootstrap, Plan, Persist, and autonomous dispatch;
- artifact registration and approval through Feature Events;
- private cross-repository autonomous execution with exact-target short-lived credentials;
- deterministic dispatch identity, duplicate suppression, and exact run/receipt correlation;
- separate target-installation and Runtime App access preflights;
- workflow-profile-aware Commander task contracts;
- compiled-worker allowlisting;
- current-main Gemini CLI `0.52.0` materialization;
- full external Feature lifecycle dogfood through requirement, design, implementation, review, verification, acceptance, and release Gates.

## Explicit release-matrix decision

The remaining private security-sensitive target is no longer a required v0.2 release blocker.

That target correctly failed closed when a low-risk CI-baseline Feature exposed a pre-existing cryptographic compatibility defect. The work was split into high-risk Feature `F-PASSWORD-MANAGER-CRYPTO-COMPAT-0001`, which completed Requirement Review, Design Review, and Plan. Before the v0.2 release decision it had already entered `implementation: WORKING` at revision 9 through a normal Feature Event/Persist transition.

The release decision intentionally **does not** mark that Feature DONE, PASS any remaining Gate, or waive any lifecycle requirement. It remains active post-v0.2 hardening work.

The required v0.2 lifecycle matrix is narrowed to:

1. the completed public external full-lifecycle dogfood; and
2. the completed private repeated-dogfood target A lifecycle.

This still satisfies the release requirement for repeated cross-repository evidence while avoiding coupling the v0.2 control-plane release to completion of target-specific Argon2 implementation work.

## Release baseline policy

A formal v0.2 release candidate may be cut when all of the following are true:

- Feature-context dogfood is fully closed with green validation evidence;
- the narrowed required cross-repository lifecycle matrix is complete;
- the formal `release/v0.2.0.yaml` manifest declares only capabilities, validators, schemas, profiles, entry points, and evidence present on the release commit;
- `VERSION` is `0.2.0` only in the final reviewed release-baseline change;
- `CHANGELOG.md` contains the `0.2.0` release section;
- repository validation and the stable `required-pr-gate` are green on the final release-baseline PR;
- the merged release commit is rechecked before tag publication;
- production callers continue to pin immutable full commit SHAs.

## Scope control

Do not add one-shot Feature-specific recovery workflows to satisfy this baseline. New dogfood failures must either use an existing generic recovery/remediation mechanism or become a reusable control-plane capability with deterministic validation and documented authority boundaries.

Target-specific post-release hardening work may continue independently, but must preserve Feature Event persistence, optimistic revision checks, independent Gates, and worker authority boundaries.
