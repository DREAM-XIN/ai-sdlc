# AI-SDLC v0.2 stabilization baseline

This document defines the stabilization boundary for the next AI-SDLC baseline after `0.1.0`.

The purpose of v0.2 is not to redesign lifecycle semantics. It is to make the already-proven autonomous and cross-repository execution paths repeatable, observable, least-privilege, and releaseable across materially different target repositories.

## Proven capabilities

The following capabilities are already implemented on `main` and are treated as part of the v0.2 candidate surface:

- provider-neutral Commander and Runtime Router boundaries;
- autonomous `gh-aw` execution with bounded Safe Output Draft PR creation;
- Feature-specific execution context propagation, including linked Feature Issue context;
- durable review remediation tasks without reopening completed work stages;
- trusted Issue Comment command transport for Bootstrap, Plan, Persist, and autonomous dispatch;
- artifact registration and approval through Feature Events;
- cross-repository autonomous handoff into private target repositories;
- deterministic cross-repository dispatch identity, duplicate suppression, and exact receipt correlation;
- least-privilege Runtime GitHub App delegation scoped to the exact target repository;
- provider-neutral cross-repository runtime installation preflight;
- compiled-worker allowlisting at the low-level autonomous gateway;
- full external Feature lifecycle dogfood through requirement, design, implementation, review, verification, acceptance, and release Gate completion.

## v0.1 -> v0.2 capability increment

v0.1 established the durable protocol, deterministic control plane, manual runtime contract, Project Adapter, Feature Events, Gate/Evidence semantics, and a reference autonomous runtime.

v0.2 stabilizes the execution layer around that protocol:

1. **Autonomous Feature context** — workers receive concrete Feature-specific outputs and linked Issue context instead of relying on generic role prompts.
2. **PR lifecycle automation** — review and verification evidence can be collected into Feature state without manually authoring Event YAML for normal PR flows.
3. **Review remediation** — `CHANGES_REQUESTED` can create durable remediation tasks and replay the original implementation role without granting the worker review or Gate authority.
4. **Provider/runtime separation** — runtime, provider, and model selection remain outside lifecycle authority, with effective model metadata made auditable.
5. **Cross-repository command transport** — target repositories can invoke trusted control-plane operations without copying lifecycle logic.
6. **Cross-repository autonomous execution** — the trusted control repository can execute bounded work against a private target repository and return results through the existing Feature Event/Persist path.
7. **Idempotent dispatch and receipts** — semantic dispatch identities prevent duplicate autonomous side effects and correlate command receipts to exact downstream runs.
8. **Installation preflight and worker allowlisting** — target Runtime App access can be checked without mutation and arbitrary workflow injection is rejected.

## Repeated cross-repository dogfood matrix

Before a formal `0.2.0` release candidate is declared, run the same generic installation and lifecycle path against at least two materially different target repositories.

### Candidate A: DREAM-XIN/SmartClipboard

Stack characteristics:

- Tauri + React desktop shell;
- Flutter mobile application;
- shared TypeScript/domain packages;
- Supabase-backed integration paths;
- native desktop/mobile build considerations.

This candidate exercises multi-language, multi-runtime, native-shell, and monorepo-style Project Adapter behavior.

### Candidate B: DREAM-XIN/password-manager

Stack characteristics:

- Java 21 + Spring Boot backend;
- Vue 3 + Vite + Element Plus frontend;
- browser extension;
- Capacitor mobile client;
- MySQL 8 and Docker Compose;
- security-sensitive product constraints.

This candidate exercises backend/frontend ownership roots, heterogeneous verification commands, security-sensitive review, and a non-`main` default branch (`develop`).

For each candidate, the dogfood should prove:

- installation/bootstrap from the target repository without copying control-plane implementation;
- a non-default Feature branch owns authoritative Feature state;
- requirement/design artifacts are registered and approved through Feature Events;
- autonomous implementation produces a bounded Draft PR to the Feature branch, never the default branch;
- duplicate dispatch is suppressed for the same semantic work unit;
- review remediation can be executed without worker Gate authority;
- repository-specific verification commands produce durable evidence;
- acceptance/release state is reached only through the normal lifecycle;
- the final target Feature Manifest reaches workflow `DONE`.

## Release baseline policy

A formal v0.2 release candidate should be cut only after:

- `F-FEATURE-CONTEXT-0001` is fully closed with green validation evidence;
- stale/superseded generated runtime PRs are reconciled;
- both repeated cross-repository dogfoods complete or an explicit release decision narrows the required matrix;
- README and release documentation describe the implemented architecture rather than the earlier v0.1 milestone plan;
- the machine-readable v0.2 release manifest contains only capabilities and validators present on the release commit;
- `VERSION` is changed from `0.1.0` only in the final reviewed release-baseline change, not during stabilization.

## Scope control

Do not add one-shot Feature-specific recovery workflows to satisfy this baseline. A new dogfood failure must either:

- be resolved through an existing generic recovery/remediation mechanism; or
- become a generic control-plane capability with deterministic validation and documented authority boundaries.

Feature-specific workarounds are evidence of a missing reusable capability, not release completion.
