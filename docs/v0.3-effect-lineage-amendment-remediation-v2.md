## 1. Verified baseline that constrains the remediation

The current frozen/runtime contract deliberately uses `dispatch.launch.authorized` as the launch linearization point.

The ordering already frozen for v0.3 is:

```text
cancel/supersede durable before dispatch.launch.authorized
  -> launch forbidden

dispatch.launch.authorized durable before cancel/supersede
  -> that exact authorized external launch may still complete
```

Therefore a stale runner may resume after cancellation/supersession and execute only the exact already-authorized `external_dispatch_key`.

The current Store implementation is consistent with that contract:

- `plan_authorize_launch(...)` durably appends `dispatch.launch.authorized` before the external call;
- `plan_launch_lookup(...)` only accepts an `external_dispatch_key` already present in the Operation projection's `authorized_dispatches`;
- `lookup = NOT_LAUNCHED` is therefore an external observation about an already-correlated authorized key, not a revocation of its durable launch authorization;
- takeover starts a new Operation generation but does not erase an already-durable launch authorization for the old exact dispatch.

This remediation intentionally **does not introduce a new post-authorization revocation primitive**. The amendment stays compatible with the existing `dispatch(key) / lookup(key)` runtime contract and preserves the existing launch linearization semantics.

# 2. MAJOR-1 remediation — `NOT_LAUNCHED` does not revoke durable launch authority

## 2.1 Required distinction

Lineage recovery MUST distinguish these predecessor classes:

```text
NEVER_LAUNCH_AUTHORIZED
LAUNCH_AUTHORIZED_UNCONFIRMED
LAUNCH_AUTHORIZED_NOT_LAUNCHED_OBSERVED
LAUNCHED_CORRELATED
UNKNOWN
```

The distinction is based on durable control-plane history plus trusted runtime evidence.

### `NEVER_LAUNCH_AUTHORIZED`

The durable Store contains no `dispatch.launch.authorized` for the predecessor exact reservation/key, and trusted recovery has no evidence that an external launch occurred outside the reviewed protocol.

### `LAUNCH_AUTHORIZED_UNCONFIRMED`

`dispatch.launch.authorized` is durable, but no conclusive trusted runtime receipt/observation has established whether the exact authorized launch executed.

### `LAUNCH_AUTHORIZED_NOT_LAUNCHED_OBSERVED`

`dispatch.launch.authorized` is durable and a trusted lookup currently returns `NOT_LAUNCHED` for that exact existing key.

This state is **not equivalent to `NEVER_LAUNCH_AUTHORIZED`**. The old launch authority has already crossed the frozen linearization point and may still be exercised by a stale runner.

### `LAUNCHED_CORRELATED`

Trusted evidence proves the exact existing key launched and identifies/correlates the receipt.

### `UNKNOWN`

Trusted evidence cannot conclusively determine external launch state.

## 2.2 Normative invariant

The amendment MUST add this invariant:

> `NOT_LAUNCHED` is an observation of current external state, not a revocation receipt for an already-durable `dispatch.launch.authorized`. A successor external identity may not be activated while an earlier exact predecessor still has executable launch authority.

Equivalently:

```text
launch_authorized(K0)
AND lookup(K0) == NOT_LAUNCHED
DOES NOT IMPLY
safe_to_retire_launch_authority(K0)
```

Candidate change, Feature revision change, Operation takeover, cancellation, supersession, restart, missing callback, or a later successor proposal do not alter this rule.

## 2.3 Replacement for Design §8.4 — predecessor proves NOT_LAUNCHED

The previous Design §8.4 text is replaced by the following semantics.

### Case A — predecessor was never launch-authorized

If trusted durable Store history proves predecessor `K0` **never crossed `dispatch.launch.authorized`**, and trusted evidence proves it did not launch:

- exact retry of `K0`, if still desired, proceeds only through normal current reservation/claim/launch-authorization fences;
- if current authoritative truth now requires exact successor `K1`, the system MAY durably resolve/retire `K0` as not launched and then atomically activate `K1` through lineage CAS;
- a new reservation/key for `K1` may be created only after the predecessor retirement/resolution is durable and all current Feature/candidate/generation fences pass.

### Case B — predecessor was launch-authorized and lookup is currently NOT_LAUNCHED

If `dispatch.launch.authorized(K0)` is already durable and trusted lookup currently returns `NOT_LAUNCHED`:

- `K0` MUST NOT be retired merely because of that observation;
- `K1` MUST remain a successor proposal only;
- no new reservation for `K1` may be created;
- no new `external_dispatch_key` for `K1` may be minted;
- no external dispatch for `K1` may be authorized;
- recovery MAY continue only against the **same existing predecessor key `K0`** under the frozen exact-key recovery/linearization rules, or the lineage remains `BLOCKED`;
- if a stale runner resumes, it may perform only the exact pre-authorized `K0` launch using the existing key; that possibility is precisely why `K1` remains blocked.

A successor becomes eligible only if later trusted evidence reaches one of these stronger states:

1. `K0` is conclusively LAUNCHED and is correlated/adopted, after which current applicability is resolved before any genuinely required successor is activated; or
2. `RETIRE_OBSOLETE_NO_DUPLICATE_PROVEN` supplies durable proof strong enough to establish that the already-authorized `K0` can no longer execute or cannot overlap/duplicate `K1`.

The current v0.3 runtime contract has no general revocation primitive, so a plain `NOT_LAUNCHED` lookup after launch authorization does **not** satisfy item 2.

## 2.4 Replacement for Design §9 state interpretation

The previous state description is qualified as follows:

```text
lookup(external_dispatch_key)
  -> NOT_LAUNCHED
  -> LAUNCHED(receipt)
  -> UNKNOWN
```

These lookup values must be interpreted together with durable launch-authorization history.

The effective lineage safety states include:

```text
NEVER_LAUNCH_AUTHORIZED_NOT_LAUNCHED
LAUNCH_AUTHORIZED_UNCONFIRMED
LAUNCH_AUTHORIZED_NOT_LAUNCHED_OBSERVED
LAUNCHED_AWAITING_CORRELATION
LAUNCHED_CORRELATED
UNKNOWN
LEGACY_UNRESOLVED_LINEAGE
```

For successor activation:

- `NEVER_LAUNCH_AUTHORIZED_NOT_LAUNCHED` may be resolvable by `PROVE_NOT_LAUNCHED`;
- `LAUNCH_AUTHORIZED_UNCONFIRMED` blocks;
- `LAUNCH_AUTHORIZED_NOT_LAUNCHED_OBSERVED` blocks;
- `UNKNOWN` blocks;
- `LAUNCHED_AWAITING_CORRELATION` blocks;
- `LEGACY_UNRESOLVED_LINEAGE` blocks.

## 2.5 Replacement for Design §10.2 / Amendment §3.6 — `PROVE_NOT_LAUNCHED`

`PROVE_NOT_LAUNCHED` MUST carry and validate both:

```text
trusted external non-launch evidence
AND
durable launch-authorization history for the predecessor
```

Its successor-activation meaning is bounded:

### Allowed successor retirement path

`PROVE_NOT_LAUNCHED` may retire predecessor `K0` and make a different successor eligible **only when trusted durable history proves that no still-executable `dispatch.launch.authorized(K0)` exists**.

For the current frozen launch contract, the normal proof is:

```text
no durable dispatch.launch.authorized for K0
+ trusted proof that K0 did not launch
```

### Launch-authorized predecessor

If `dispatch.launch.authorized(K0)` is durable, then:

```text
lookup(K0) == NOT_LAUNCHED
```

is insufficient to retire `K0` for successor activation.

The allowed outcomes are:

```text
same-existing-key recovery for K0 under existing fences
OR
REMAIN_BLOCKED
```

until stronger trusted proof satisfies `RETIRE_OBSOLETE_NO_DUPLICATE_PROVEN` or the existing launch is conclusively correlated.

The resolution record MUST bind whether a durable predecessor launch authorization exists and MUST reject a `PROVE_NOT_LAUNCHED -> successor activation` decision when such authorization remains executable.

## 2.6 Qualification for `RETIRE_OBSOLETE_NO_DUPLICATE_PROVEN`

For a predecessor that already crossed `dispatch.launch.authorized`, this outcome requires evidence **strictly stronger than a current `NOT_LAUNCHED` observation**.

Acceptable classes include only reviewed trusted proofs such as:

- authoritative external invalidation/cancellation that is itself durable and guarantees the exact old authorized key can no longer execute;
- a trusted gateway/runtime fencing receipt that every possible launcher must honor and that linearizes before successor activation;
- authoritative external scope/namespace proof establishing that execution of `K0` cannot duplicate or overlap the successor effect;
- another independently reviewed proof with equivalent no-duplicate strength.

Because the current `dispatch(key) / lookup(key)` contract has no generic revocation operation, this amendment does not assume such a fence exists.

If a future implementation introduces post-authorization revocation, that revocation protocol must be separately reviewed and must define an ordering/linearization relation against:

```text
dispatch.launch.authorized
stale runner execution
operation cancellation/supersession
runtime/gateway dispatch admission
successor activation
```

Every launcher/gateway capable of executing the old key would have to honor that fence. Until then, fail closed.

## 2.7 Same-key recovery does not authorize successor work

Same-key recovery is deliberately narrow.

If old exact `K0` is already launch-authorized but currently `NOT_LAUNCHED`, recovery may only continue/correlate `K0` using the existing stable `external_dispatch_key` according to frozen recovery rules.

It MUST NOT reinterpret a new candidate/revision as permission to:

- mutate `K0`'s exact candidate/revision binding;
- mint a new key for `K1`;
- dispatch `K1` before predecessor safety is resolved.

If current truth no longer wants `K0` and no stronger proof exists, the correct state is `BLOCKED`.

## 2.8 Deterministic stale-runner adversarial test

The amendment MUST add a deterministic test equivalent to:

```text
K0 exact reservation exists
→ dispatch.launch.authorized(K0, E0) becomes durable
→ stale Runner A pauses before external dispatch(E0)
→ trusted lookup(E0) returns NOT_LAUNCHED
→ current Feature/candidate truth now proposes K1 in same effect lineage
→ recovery records/reuses successor proposal K1
→ recovery attempts PROVE_NOT_LAUNCHED retirement
→ protocol rejects K0 retirement for successor activation because launch authorization is durable
→ assert no reservation/external key/launch authorization exists for K1
→ Runner A resumes
→ Runner A may execute only dispatch(E0)
→ system correlates/adopts E0 if launched, or remains same-key recovery/BLOCKED
→ assert there is no execution in which both K0/E0 and a new K1/E1 can launch from the NOT_LAUNCHED observation
```

A second branch SHOULD cover the never-authorized case:

```text
K0 has no dispatch.launch.authorized
→ trusted proof establishes NOT_LAUNCHED
→ current truth requires K1
→ durable lineage retirement of K0 wins CAS
→ only then K1 may be activated and receive a new exact reservation/key
```

# 3. MAJOR-2 remediation — candidate-head change requires fresh exact work, not immediate external dispatch

## 3.1 Replacement invariant

The amendment MUST explicitly replace the ambiguous old statement "new candidate requires new semantic dispatch" with this invariant:

> A candidate-head change invalidates stale Reviewer/QA evidence and requires fresh exact candidate-bound work identity/proposal for the current candidate. Candidate change alone never authorizes a new external reservation, `external_dispatch_key`, launch authorization, or external dispatch while an overlapping lineage predecessor is unresolved.

This preserves exact candidate/result binding without creating a lineage bypass.

The sequence is:

```text
candidate A work/evidence becomes stale when head moves to B
→ A result cannot Persist for B
→ trusted planner derives fresh exact candidate-bound semantic material for B
→ if A has no overlapping unresolved predecessor, B may activate normally
→ if A is UNKNOWN / launch-authorized-unconfirmed / launch-authorized-NOT_LAUNCHED / otherwise unresolved in the same lineage,
   B is only a blocked successor proposal
→ B receives no independent external reservation/key/dispatch until lineage safety clears
```

Candidate change therefore has two separate consequences that MUST NOT be conflated:

1. **Evidence/work applicability:** stale A evidence is invalid; B needs fresh exact candidate-bound work/proposal.
2. **External launch eligibility:** B may launch only after the lineage gate proves no unresolved overlapping predecessor can still execute/duplicate it.

## 3.2 Explicit replacement for frozen Recovery Contract candidate row

When a later independently approved amendment is applied to the frozen Release Spec, the existing recovery row:

```text
Reviewer/QA result for stale candidate head | reject; new candidate requires new dispatch
```

MUST be replaced with semantics equivalent to:

```text
Reviewer/QA result for stale candidate head |
reject stale result; current candidate requires fresh exact candidate-bound work identity/proposal;
new external reservation/key/dispatch is permitted only after effect-lineage gating proves any overlapping predecessor safely resolved
```

The `PR head changes` row remains valid as evidence invalidation, but SHOULD be qualified to cross-reference lineage gating when fresh Reviewer/QA work would overlap an unresolved predecessor.

## 3.3 Explicit replacement for frozen §19.3 Candidate binding test

The old test ending:

```text
Reviewer/QA dispatched at candidate SHA A
→ candidate moves to SHA B
→ result for A arrives
→ translator/Persist rejects A
→ B requires new semantic dispatch
```

MUST be replaced by:

```text
Reviewer/QA exact work is bound to candidate SHA A
→ candidate moves to SHA B
→ result for A arrives
→ translator/Persist rejects A as stale
→ trusted planner derives fresh exact candidate-bound work identity/proposal for B
→ if A is an unresolved overlapping predecessor in the same effect lineage,
   B remains BLOCKED and receives no new external reservation/key/dispatch
→ only after predecessor safety is durably resolved may B be activated
→ when activated, B uses its own exact candidate-B semantic reservation/key; A evidence is never rebound to B
```

This test simultaneously proves candidate immutability and lineage effect safety.

## 3.6 Candidate-change adversarial test

The amendment-required deterministic suite MUST include:

```text
Reviewer/QA dispatch K0 bound to candidate A
→ K0 launch state becomes UNKNOWN, or launch authorization is durable and current lookup is NOT_LAUNCHED
→ candidate moves A -> B
→ stale result/evidence for A is rejected
→ fresh exact candidate-B work/proposal K1 is derived
→ assert K1 has different exact candidate-bound semantic material
→ assert K1 is in the same causal effect lineage when work overlaps
→ assert K1 has no reservation/external_dispatch_key/launch authorization while K0 is unresolved
→ after conclusive lineage-safe resolution, K1 may activate under current fences
```

This replaces any interpretation that candidate B automatically receives a new external dispatch merely because the exact candidate head changed.

# 4. Resulting consolidated normative rules

After applying this remediation to the original author proposal, the intended amendment semantics are:

1. `semantic_effect_key` remains exact revision/stage/task/role/candidate-bound identity.
2. `effect_lineage_id` remains the cross-revision/candidate continuity domain for overlapping causal work.
3. The lineage gate occurs before creation of a new exact external reservation.
4. `dispatch.launch.authorized` remains the frozen launch linearization point.
5. The amendment introduces **no generic post-authorization revocation primitive**.
6. `NOT_LAUNCHED` after durable launch authorization does not retire that authorization.
7. A launch-authorized predecessor observed `NOT_LAUNCHED` permits only same-existing-key recovery or `BLOCKED`, unless stronger reviewed no-duplicate proof exists.
8. A never-launch-authorized predecessor may be retired by `PROVE_NOT_LAUNCHED` only with trusted durable non-launch proof.
9. Candidate change invalidates stale candidate evidence.
10. Candidate change requires fresh exact candidate-bound work identity/proposal.
11. Candidate change alone never authorizes new reservation/key/dispatch while an overlapping predecessor is unresolved.
12. `head_change_requires_new_semantic_dispatch` and `new-head-requires-new-semantic-dispatch` are explicitly replaced by lineage-gated candidate semantics.
13. The amended planning-manifest validator must reject the old contradictory machine-readable form.
14. UNKNOWN, launch-authorized-unconfirmed, launch-authorized-NOT_LAUNCHED, cancellation, supersession, revision bump, candidate change, generation takeover, restart, and missing callback cannot be used as a new-key escape hatch.
15. No external exactly-once claim is introduced.
