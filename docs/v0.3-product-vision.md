# AI-SDLC v0.3 product vision: AI Operator

Status: Review Draft

Tracking issue: #205

## Version theme

**AI-Operated SDLC**

AI-SDLC v0.2 established a durable, deterministic and auditable control kernel for agentic software development. v0.3 productizes that control plane behind an AI Operator so ordinary users can drive development through natural language without learning GitHub, Feature Manifest, revision, Event, Gate, Plan or Persist mechanics.

The product boundary is:

```text
Conversation / AI Client
        ↓
AI Operator
        ↓
AI-SDLC Control Kernel
        ↓
GitHub / CI / Role Workers
```

## North star

A user should be able to say:

> Take over this project and add email/password login with appropriate security controls.

The system should understand the repository, ask only material product or authorization questions, coordinate bounded independent workers, preserve lifecycle authority in AI-SDLC, recover across interrupted AI sessions, and return a human-readable summary of progress, risks, evidence and required decisions.

Normal Feature work should not require users to:

- open GitHub;
- edit AI-SDLC YAML;
- create Feature branches manually;
- issue `/ai-sdlc` commands;
- reason about revisions;
- invoke Plan or Persist manually;
- inspect GitHub Actions for routine progress;
- move prompts between Product, Architect, Developer, Reviewer and QA chats;
- repeatedly send `continue`.

Initial GitHub App/OAuth installation or credential authorization may require an explicit external authorization step. After that setup, normal Feature execution should not require manual GitHub operations.

## Core principles

### Operator is not authority

```text
Models propose.
AI-SDLC validates.
Workers execute.
GitHub records.
```

The Operator may interpret intent, plan orchestration, invoke typed tools, dispatch workers, collect results and request lifecycle persistence. It may not bypass deterministic state transitions, revisions, Gates, Evidence requirements, branch protections or authorization policy.

### GitHub remains the durable fact source

Chat context may disappear. Feature state may not.

A new AI session must be able to recover current Feature progress, outstanding decisions and auditable evidence from durable state without relying on the previous conversation transcript.

### No second Feature truth

Operator persistence stores orchestration facts such as operation identity, dispatch claims, callback correlation, retries and waiting state. It must derive lifecycle truth from authoritative AI-SDLC Feature state instead of maintaining a competing copy of current stage, Gate status or artifact authority.

### Independent roles remain independent

Operator coordination must not collapse development, independent review, QA and acceptance into one mixed-authority execution.

Independence is enforced through worker identity, role, capability, task context, repository permission and evidence ownership rather than through separate user-facing chat windows.

### Workers return evidence, not lifecycle mutations

A Worker Result must never contain an arbitrary executable Feature Event.

The trusted path is:

```text
Role Worker Result
      ↓
Role-specific Trusted Translator
      ↓
Bounded Feature Event
      ↓
Existing validation / Persist
```

For example:

```text
Developer Result → Developer Result Translator
Reviewer Result  → Review Verdict Translator
QA Result        → Verification Verdict Translator
```

### Authorization is trusted policy

Ordinary engineering constraints may come from Project Adapter context, but authorization boundaries must come from protected default-branch configuration, installation-level configuration or the trusted control repository.

A Feature branch may tighten permissions but must never expand its own authorization envelope.

### Automatic execution stops only at meaningful boundaries

A durable operation should continue automatically through ordinary lifecycle work and external waits. Stable user-visible stopping states are:

```text
NEEDS_USER
BLOCKED
DONE
CANCELLED
```

`WAITING_EXTERNAL` means the system is waiting for a Worker, CI, PR or callback and should resume without requiring another user message.

## User-visible operator state

```text
RUNNING

WAITING_EXTERNAL
├── WAITING_WORKER
├── WAITING_CI
├── WAITING_PR
└── WAITING_CALLBACK

NEEDS_USER
├── NEEDS_CLARIFICATION
├── NEEDS_AUTHORIZATION
├── NEEDS_ACCEPTANCE
└── NEEDS_CREDENTIAL_SETUP

BLOCKED
DONE
CANCELLED
```

These states are a user-facing orchestration projection, not new Feature lifecycle authority.

## Decisions and authorization

A user's `yes`, `continue` or `looks good` must never be interpreted as a universal approval.

Every authorization-worthy decision must be represented as a concrete Decision object bound to the exact target, including as applicable:

- decision id and type;
- Feature id;
- expected revision;
- target ref;
- candidate head SHA;
- allowed choices;
- requester and responder identity;
- expiry.

Only the minimum auditable decision record should be persisted. Full chat transcripts and unnecessary sensitive content should not be stored as decision evidence.

## Durable operation and notification

Operator execution must survive chat-session interruption. The preferred architecture is short executions plus durable append-only Operation Events and event-driven resume rather than a long-running in-memory loop.

When execution reaches a user-relevant state while the user is offline, a Notification Outbox records events such as:

```text
decision.requested
operation.blocked
operation.completed
authorization.expiring
```

AI client adapters may push these notifications when supported. Clients without push support must be able to discover unread notifications, pending Decisions and unfinished Operations when a new session starts.

## v0.3.0 release slice

v0.3.0 intentionally starts with an already-installed AI-SDLC project and proves one safe vertical loop:

```text
AI Client
→ capability discovery / status
→ start or resume durable Operation
→ Developer
→ Independent Reviewer
→ Remediation when required
→ Independent Re-review
→ QA
→ NEEDS_USER / DONE
```

The release must prove that this loop is durable, idempotent, recoverable, auditable and role-isolated while preserving existing lifecycle authority.

Full Requirement/Design orchestration and automatic Project Takeover are subsequent v0.3.x enhancements once this vertical slice is stable.

## v0.3.x direction

After the core loop is proven, v0.3.x may extend Operator orchestration to Product, Requirement Review, Architecture, Design Review and Human/Product Acceptance, followed by project inspect/install/upgrade flows.

Project Takeover should use the same trusted control boundaries; it must not become a parallel installer that bypasses existing target installation contracts or runtime preflights.

## Success definition

AI-SDLC v0.3 succeeds when an ordinary user can operate a real Feature through natural language while the system preserves the same deterministic authority, independent review, evidence and GitHub auditability established by v0.2.

Users see goals, progress, risk, questions, decisions and results. Internal protocol mechanics remain available for audit and recovery but are no longer the primary user interface.
