# v0.3 Release Spec Amendment Proposal — Effect Lineage and UNKNOWN Resolution

Status: **PROPOSED — independent exact-head amendment review required**

Tracking issue: #219  
Parent planning issue: #205  
Frozen Release Spec review baseline: `2e1fd261d4f1142b6b1d6fdf1b86e0027254f0c4` (PR #206)  
Current post-implementation main baseline observed before this proposal: `32387383f8060a0013f70be090d7dd03c0a433fe`

This document proposes a normative amendment to the frozen v0.3 Release Spec. It does **not** itself modify `docs/v0.3-release-spec.md` or `release/v0.3.0-draft.yaml`, and it is not an approval/freeze receipt.

The frozen baseline remains authoritative until an independent reviewer evaluates the exact amendment head and explicitly authorizes amendment freeze/merge.

## 1. Amendment reason

The frozen Release Spec correctly makes exact external-effect identity generation-independent, but the exact `semantic_effect_key` still includes Feature revision, stage and candidate facts.

Therefore the current normative text does not fully prevent this sequence:

```text
exact effect K0 @ Feature revision R
→ launch state UNKNOWN
→ authoritative Feature state advances to R+1
→ planner derives different exact key K1
→ K1 could look independent even when it represents the same unresolved real-world work
```

Operation-generation inheritance does not close this cross-Feature-revision continuity gap.

The amendment MUST add a stable Effect Lineage above exact semantic reservations and a bounded UNKNOWN-resolution protocol before v0.3 may rely on release-level effect-safety claims.

## 2. Amendment principle

The frozen exact reservation model remains valid, but its role is narrowed explicitly:

> `semantic_effect_key` identifies one exact revision/stage/task/role/candidate-bound semantic reservation. It is not, by itself, the complete cross-revision identity of a real-world external work lineage.

A new durable `effect_lineage_id` identifies the continuity domain across exact reservations that remain causally the same real-world work.

Feature revision, candidate SHA, Operation generation, Operation id, restart, or chat/session change MUST NOT by themselves create a new lineage or release an unresolved predecessor.

## 3. Proposed normative Release Spec changes

### 3.1 Amend Section 7 — Operation generation and external semantic side-effect reservation

Retain the current exact `semantic_effect_key` material and stable `external_dispatch_key` rules.

Add the following normative requirements:

1. Every launch-eligible exact semantic reservation MUST belong to one trusted durable `effect_lineage_id`.
2. `effect_lineage_id` MUST be derived from trusted durable causal-work semantics and MUST NOT change merely because Feature revision, candidate projection, Operation generation, Operation id, process/session identity, or runner identity changes.
3. The trusted planner MUST consult lineage state before creating a new exact semantic reservation.
4. A new exact reservation/external key MUST NOT be created when an equivalent/successor exact effect is blocked by an unresolved lineage predecessor.
5. Concurrent planners MUST converge through the protected Store CAS path so one unresolved predecessor cannot acquire multiple active launch-eligible descendants.

### 3.2 Add a new normative section — Cross-revision Effect Lineage

Normative model:

```text
Effect Lineage L
  member K0 @ exact state R
     ↓ predecessor_of
  member/proposal K1 @ exact state R+1
```

Required semantics:

- `K0` and `K1` may have different exact `semantic_effect_key` values while still belonging to the same lineage.
- A proposed descendant is a **successor proposal** until lineage safety permits activation.
- A successor proposal has no independent external dispatch identity while its predecessor is unresolved.
- `predecessor` is the prior exact member whose external resolution constrains successor launch eligibility.
- `blocks_on` is derived from durable lineage/external-state facts.
- `supersedes` records that old exact work is no longer the current desired exact work, but it does not release blocking.
- `adopts` records trusted correlation of an already-launched predecessor effect; adoption never launches a new effect.
- v0.3 launch-eligible lineage members form a single ordered chain; concurrently active sibling descendants are forbidden.

### 3.3 Define lineage identity requirements

Normative lineage material MUST be trusted and causal, conceptually including:

```text
target_repository
feature_id
operation_profile
effect_kind
role
causal_work_id
external_effect_scope
```

The exact implementation may use different reviewed field names, but the semantics MUST distinguish:

- same unresolved real-world work;
- legitimate successor exact work within that lineage;
- genuinely different new work/effect scope.

`causal_work_id` MUST come from durable lifecycle/task provenance such as a stage execution episode or authoritative remediation task, not an AI/client-generated random discriminator.

### 3.4 Amend launch planning

Before creating a new exact semantic reservation:

1. derive current trusted lineage identity;
2. reconstruct the current lineage leaf/predecessor;
3. determine whether the requested exact effect is an exact replay, blocked successor, or genuinely distinct lineage;
4. if blocked, persist/reuse a successor proposal and return/project `BLOCKED`;
5. do not create a new exact reservation or new `external_dispatch_key` until predecessor safety is conclusively resolved;
6. after safe resolution, re-read current Feature/candidate/generation/policy fences before activating a successor or retry.

### 3.5 Amend UNKNOWN semantics

`UNKNOWN` MUST be treated as unresolved lineage safety state, not merely an unresolved exact-key state local to one Feature revision.

The following states MUST block a new independent descendant:

```text
LAUNCH_AUTHORIZED_UNCONFIRMED
UNKNOWN
LAUNCHED_AWAITING_CORRELATION
LEGACY_UNRESOLVED_LINEAGE
```

Missing local `worker.dispatched`, callback, or journal acknowledgement never proves that launch did not occur.

### 3.6 Define allowed resolution outcomes

The protocol MUST support only bounded trusted outcomes equivalent to:

```text
CORRELATE_EXISTING_RECEIPT
PROVE_NOT_LAUNCHED
RETIRE_OBSOLETE_NO_DUPLICATE_PROVEN
REMAIN_BLOCKED
```

Normative rules:

- `CORRELATE_EXISTING_RECEIPT`: trusted evidence proves predecessor LAUNCHED; adopt/correlate the existing receipt and never relaunch it.
- `PROVE_NOT_LAUNCHED`: trusted evidence proves predecessor did not launch; exact retry may reuse the same stable key, or an obsolete predecessor may be retired before a current successor is activated.
- `RETIRE_OBSOLETE_NO_DUPLICATE_PROVEN`: allowed only when trusted durable evidence proves a successor cannot duplicate the predecessor's real-world effect despite the prior unresolved local state.
- `REMAIN_BLOCKED`: required whenever no trustworthy proof exists.

The following MUST NOT resolve UNKNOWN or authorize a new independent dispatch:

```text
generic retry
ignore
force
Feature revision bump
candidate SHA change
Operation generation change
Operation id change
Operation cancellation
process restart
missing local callback/receipt
```

### 3.7 Add bounded human/trusted Effect Resolution Authority

The Release Spec MUST define a bounded `EffectResolutionAuthority` or semantic equivalent.

Authority MUST come from trusted protected/default-branch, installation-level, or trusted-control policy. A Feature branch, Worker, callback, or ordinary AI client MUST NOT grant itself this authority.

A resolution MUST be bound to at least:

```text
resolution_id
target_repository
feature_id
effect_lineage_id
predecessor_semantic_effect_key
predecessor_external_dispatch_key
current_operation_id
current_operation_generation
current_feature_revision
current_target_ref
current_candidate_head_sha_when_applicable
successor_proposal_id_when_applicable
successor_proposed_semantic_effect_key_when_applicable
allowed_resolution_choice
trusted_policy_ref_or_digest
resolver_identity
evidence_refs_and_digests
resolved_at
```

Resolution application MUST re-read current Feature/lineage/Operation/policy state under CAS and reject stale or mismatched decisions.

A resolution does not itself dispatch. Normal reservation, claim, launch-authorization, candidate, generation, cancellation and policy fences MUST pass afterward.

There MUST NOT be a generic `FORCE_RETRY`, `IGNORE_UNKNOWN`, `DROP_RESERVATION`, or `NEW_KEY_ANYWAY` choice.

### 3.8 Amend restart/generation takeover semantics

Existing generation takeover rules remain, with this stronger invariant:

```text
G: lineage L / exact K0 / external key E / UNKNOWN
→ G crashes
→ G+1 takeover
```

`G+1` inherits/reconstructs lineage `L`, predecessor `K0` and key `E`. If current Feature revision/candidate now proposes exact `K1`, `K1` is blocked as a successor proposal until `K0` is conclusively resolved.

Generation, revision, candidate projection, or Operation replacement must never automatically mint an independent descendant key.

### 3.9 Amend stale/obsolete exact-work handling

When authoritative Feature truth makes the old exact effect obsolete:

- record the obsolete/superseding intent durably;
- do not silently discard UNKNOWN state;
- candidate SHA or revision mismatch alone is not retirement proof;
- require `PROVE_NOT_LAUNCHED`, `CORRELATE_EXISTING_RECEIPT`, or `RETIRE_OBSOLETE_NO_DUPLICATE_PROVEN` before a potentially overlapping successor becomes launch-eligible;
- a confirmed launched predecessor result may be orphaned/rejected for current Feature Persist if stale, but launch knowledge remains part of lineage safety history.

### 3.10 Amend protocol migration requirements

The preferred migration is additive:

- retain `state/operator/v1`;
- retain existing immutable `semantic_effect_key` reservations and their stable external keys;
- introduce a versioned lineage schema/journal, conceptually `ai-sdlc.effect-lineage/v1` and `ai-sdlc.effect-lineage-event/v1`;
- lineage-gate creation of future exact reservations;
- keep lineage projection rebuildable from immutable lineage facts;
- preserve existing launch/cancel/Persist linearization semantics.

Legacy exact reservations without lineage metadata remain readable.

For unresolved legacy reservations:

- trusted migration MAY attach immutable lineage metadata when causal identity can be reconstructed safely;
- UNKNOWN or launch-authorized-unconfirmed legacy reservations MUST fail closed until lineage is established;
- when overlapping lineage scope cannot be proven, mark/quarantine as `LEGACY_UNRESOLVED_LINEAGE` and block potentially overlapping new launches.

Mixed production writers are forbidden during migration: old writers that do not enforce lineage must be fenced/quiesced before lineage enforcement becomes authoritative.

## 4. Versioning impact

### 4.1 Canonical API

No `ai-sdlc.operator/v1` bump is required by this amendment because the required lineage and resolution semantics may remain behind the trusted control-plane boundary without changing existing public request/response contracts incompatibly.

If later Decision/Authorization work exposes a new public resolution capability, it must follow normal capability/versioning review.

### 4.2 Operation Event

No `ai-sdlc.operation-event/v2` bump is required solely for the lineage amendment if lineage authority is represented in a separate append-only lineage journal.

A future implementation that changes the Operation Event envelope incompatibly must receive a separate versioning review.

### 4.3 Store schema

A new explicit lineage schema version is required. Recommended conceptual identifiers:

```text
ai-sdlc.effect-lineage/v1
ai-sdlc.effect-lineage-event/v1
```

Exact file/schema names remain implementation-reviewable; the semantic compatibility rules above are normative.

## 5. Runtime compatibility

The release runtime/gateway contract remains:

```text
dispatch(external_dispatch_key, payload)
lookup(external_dispatch_key)
  -> NOT_LAUNCHED
  -> LAUNCHED(receipt)
  -> UNKNOWN
```

Lineage is a trusted control-plane gate above that contract.

The amendment MUST preserve:

- no speculative duplicate dispatch;
- stable external identity per exact activated reservation;
- deterministic lookup/correlation recovery;
- one authorized Feature Persist under existing exact Persist fences.

The amendment MUST NOT claim external exactly-once execution.

## 8. Required deterministic tests added by amendment

The frozen release test contract should be extended to require at least:

1. `UNKNOWN@R -> unrelated revision R+1 -> same work`: same lineage, no new external reservation/key/launch;
2. `UNKNOWN@R -> candidate changed but effect equivalent`: no bypass;
3. predecessor proves `NOT_LAUNCHED`: exact retry uses same key or safely retired successor becomes eligible only after durable resolution;
4. predecessor proves `LAUNCHED`: correlate/adopt existing receipt, no relaunch;
5. no trustworthy proof: remain `BLOCKED`;
6. generation takeover preserves blocking lineage;
7. concurrent planners cannot create two active descendants/external keys;
8. stale/manual resolution is rejected for wrong lineage/effect/key/Operation/generation/revision/ref/candidate/proposal/policy/evidence;
9. Operation cancellation does not retire unresolved lineage state;
10. legacy unresolved reservation without lineage fails closed rather than permitting a revision/candidate-key escape.

These deterministic tests do not substitute for #221 real-runtime fault injection.
